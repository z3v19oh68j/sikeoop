# Agent 工程架构选型

## 什么时候用
- 要给产品加「子代理 / 派活 / 调度 / 自动评审」之类能力时。
- 觉得一个提示词不够用、想上多代理之前，先过一遍这份清单。

## 核心原则（两家一手资料一致）
1. **从最简单开始**：先优化单次 LLM 调用（检索 + 示例）；不够再上工作流；还不够才上自主 agent。每加一层复杂度都要有评测证明它真的变好了。
2. **工作流 vs agent**：工作流 = 代码写死路径，可预测、省钱；agent = 模型自己决定步骤和工具，灵活但更贵、错误会累积。
3. **工具接口（ACI）当成产品来设计**：工具名、参数、文档写清楚，并测试模型能不能用对。
4. **透明**：把计划步骤展示出来；每一步从环境拿真实反馈（工具结果、测试结果）；设最大轮数等停止条件。

## 五种工作流，按需求挑
| 模式 | 适合 | 代码里怎么做 |
|---|---|---|
| 提示链 Prompt chaining | 能拆成固定几步 | 上一步输出喂下一步，中间加程序校验(gate) |
| 路由 Routing | 输入有明显类别 | 先分类（结构化输出），再选专用提示词/模型（简单题给小模型） |
| 并行 Parallelization | 子任务互不依赖，或要多次投票 | 分段并发 / 同题多跑投票；护栏单独一个调用效果更好 |
| 编排-工人 Orchestrator-workers | 子任务事先猜不到（如改多少文件） | 中心模型动态拆任务、派给工人、汇总 |
| 评估-优化 Evaluator-optimizer | 有清晰评判标准、迭代有收益 | while 循环：生成 → 评审给反馈 → 达标停止 |

## 多代理的两种交接方式（OpenAI Agents SDK 术语）
- **Agents as tools（manager）**：主代理始终掌控对话，把专家当工具调用、自己汇总答案。适合要统一护栏、一个人对最终结果负责。
- **Handoffs**：分诊代理把对话整个交给专家，专家直接回复用户。适合路由本身就是流程的一部分。
- 两者可组合：交接过去的专家仍可把别的代理当工具用。

## 步骤
1. 写下任务：步骤数能不能事先确定？有没有客观验收标准（测试、类型检查）？
2. 能确定 → 用工作流（链/路由/并行）；确定不了 → 编排-工人或自主 agent。
3. 有客观标准 → 外面套一层评估-优化循环。
4. 并行派活时划清每个工人负责的文件，避免互相覆盖。
5. 加最大轮数、超时、人工检查点；全程记录日志/trace 方便排错。
6. 先做评测集，再决定要不要加更多代理。

## 容易踩的坑
- 一上来就用重框架：抽象层把真实提示词藏起来，难调试。先直接调 API，用框架也要读懂底层。
- 一个「万能 agent」干所有事：不如多个专注的专家。
- 多代理没有停止条件 → 成本失控、错误累积。
- 工人看不到主对话：派活时必须写清目标、相关文件、验收标准。
