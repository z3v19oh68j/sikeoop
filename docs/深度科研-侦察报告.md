## 2. 输出：`run -o` 写出的 JSON

### 2.1 来源

`cli.py:76` 调 `session.run(checkpoint_path=…)`，返回值就是 `_build_summary()`（`session.py:105`）。`cli.py:78-83` 以 UTF-8、`indent=2`、`ensure_ascii=False`、`default=str` 写出，父目录不存在会自动建。

注意顺序：`cli.py:77` 先 `_print(result…)` 打印摘要，**之后**才写文件。打印出错的话（见 5.3 节编码），输出文件不会生成，只剩 checkpoint。

### 2.2 顶层字段（`session.py:618-660`）

| 字段 | 类型 | 内容 |
|---|---|---|
| `question` | string | 原问题全文 |
| `task_type` | string | 按关键词分类：`incident_analysis` / `code_review` / `literature_comparison` / `strategy_analysis` / `open_discussion`（`evidence_layer.py:168-198`） |
| `total_rounds` | int | 已完成的轮数 |
| `terminated` | bool | 是否由终止判据结束 |
| `termination_reason` | string | 见 2.5 |
| `token_estimates` | `{input, output, calls}` | 粗估：字符数 ÷ 4；`calls` 有漏算（见第 7 节） |
| `claims` | 数组 | 每条命题，见下 |
| `chains` | 数组 | 每条推理链的概要 |
| `attacks` | 数组 | 每次攻击 |
| `chain_details` | 数组 | 每条推理链的完整步骤 |
| `entropy_trajectory` | 数组 | 每轮的各项指标 |
| `evidence_pool_size` | int | 证据池条数（只有数量） |
| `divergence_map` | **string** | 四区图的文字版 |
| `natural_summary` | **string** | 中文自然语言总结 |

各数组元素：

- `claims[]`（`626-632`）：`claim_id`、`description`（截到 150 字；本身来自该命题第一条链第一步断言的前 120 字，`360`）、`alpha`（证据独立性）、`U`（0–3 的活动信号）、`state`、`chains`（**条数**）、`attacks`（**被攻击次数**）、`evidence_count`。
  - `state` 取值是 `RICH_DISAGREEMENT` / `EVIDENCE_STARVED` / `TRUE_CONSENSUS` / `FRAGILE_CONSENSUS`（`coordination_layer.py:24-28`、`246-250`）。**这不是四区**，是另一套按 `alpha × U` 分的象限。
- `chains[]`（`633-637`）：`chain_id`、`agent`（`agent_0`…）、`version`、`steps`（步数）、`attacks_received`。
- `attacks[]`（`638-643`）：`attack_id`、`attacker`、`target`（字符串 `"<agent>/<chain_id>/step<n>"`）、`claim_preview`（攻击理由，截到 300 字）。**没有**攻击的状态（成立 / 被驳回）、轮次、证据。
- `chain_details[]`（`644-651`）：`chain_id`、`agent`、`version`、`claim_id`、`status`（`active` / `broken` / `superseded` / `archived`，`content_layer.py:37-41`）、`steps[]`：`step_id`、`assertion`（全文）、`evidence`（ref 字符串数组）、`depends_on`。
- `entropy_trajectory[]`（`652-656`，来源 `419-437`）：`H_evidence`、`S_attack`、`H_part`、`H_chain`、`T_max`、`H_remaining`、`ApEn`、`S_novel`；第 10 轮起多 `H_sym` 和 `_symbol`（形如 `He低|Sa中|…` 的中文符号串，`coordination_layer.py:566-621`）。只有当轮存在链或攻击才会追加一条（`session.py:180-181`），所以长度可能小于 `total_rounds`。

输出里**没有**的：证据池内容、agent 与服务商 / 模型的对应关系（只有 `agent_0`… 按 `CHAIN_CENTRIC_AGENTS` 的顺序编号，`content_layer.py:401`）、每条命题的存活率 / trust / 所属区。

### 2.3 四区怎么得到

四区只在 `_render_divergence_map()`（`session.py:713-828`）里算，结果拼成字符串。按它的算法，可以用输出 JSON 自己重算：

对每条 claim（`719-746`）：

```
attacks        = claims[i].attacks
该命题的链      = chain_details 里 claim_id 相同的
survival_rate  = status 为 "active" 的条数 / 总条数（总条数为 0 时按 1）
trust          = alpha × (1 + survival_rate) / 2 × (1 − e^(−1.5 × attacks))

tier:
  attacks == 0                                   → unscrutinized
  alpha > 0.7 且 attacks ≥ 5 且 survival > 0.5    → ironclad
  alpha > 0.7 且 attacks < 5 且 survival > 0.5    → consensus
  alpha > 0.3                                    → contested
  其余                                           → weak
```

四区对应（`752-820`）：

| 区 | 内容 |
|---|---|
| 未审查区 | tier = `unscrutinized` |
| 共识区 | tier = `ironclad`（“铁证”）或 `consensus`（“共识”） |
| 争议区 | tier = `contested` |
| 崩塌区 | tier = `weak` 的命题，加上 `status = broken` 的链 |

说明：

- 描述为空的命题在未审查 / 共识 / 崩塌区会被跳过（`754`、`766`、`809`）。
- 争议区文字里的“核心分歧”“方法论风险”来自一次额外的 LLM 聚类（`750`、`874-912`），结果只在字符串里，JSON 没有对应字段。
- `natural_summary`（`662-711`）是另一段中文文字：共识结论（最多 5 条）、存活的推理链（最多 8 条，每条 3 步）、被击穿的链（最多 5 条）、未经验证的声明（最多 5 条）。

### 2.4 每条命题能拿到什么

| 想显示的 | 能否直接拿到 | 来源 |
|---|---|---|
| 攻击次数 | 能 | `claims[].attacks` |
| 存活率 | 不能直接拿，要算 | 2.3 的 `survival_rate` |
| 推理链 | 能 | `chain_details[]` 按 `claim_id` 过滤，含每步断言、证据 ref、依赖 |
| 针对它的攻击内容 | 间接 | `attacks[].target` 里的 `chain_id` 对回 `chain_details[].claim_id` |
| 哪次攻击成立了 | 不能 | 攻击状态没有输出 |

### 2.5 收敛信息

`termination_reason` 的取值：

| 值 | 含义 | 位置 |
|---|---|---|
| `SYSTEM_STATE_STABILIZED` | 默认策略（hsym）：连续 3 轮没有新的符号状态 | `session.py:548-550` |
| `ALL_PASS_CONSECUTIVE` | 连续 3 轮所有模型都 pass | `588-595` |
| `BUDGET_EXHAUSTED` | 到了轮数上限的前一轮 | `597-601` |
| `SEMANTIC_SATURATION` | 仅 legacy 策略 | `566-574` |
| `ENTROPY_CONVERGED: …` | 仅 legacy 策略 | `576-586` |
| 空串 | 没走到任何判据（比如上限 ≤ 4 轮） | `189-190` |

时间点：终止检查从第 4 轮才开始（`cli.py:72` 把 `min_rounds_before_termination` 设成 4；`session.py:189`）。hsym 收敛最早在第 10 轮之后（`config.py:52`、`session.py:489`；观察窗 10 轮，`coordination_layer.py:511`、`533-538`）。所以正常的一场至少 13 轮左右，除非全员提前沉默。

## 3. 进度

### 3.1 `--checkpoint` 文件

- **内容**：和最终输出相同的 `_build_summary()`，外加 `chain_statuses`（`session.py:99-100`）。`chain_statuses[]` 每条：`chain_id`、`agent`、`version`、`status`、`attacks_received`、`attacks_survived`、`steps`、`created_at`、`last_modified`（`1003-1018`）。注意最终的 `-o` 输出**没有** `chain_statuses`。
- **频率**：每轮结束后整份重写一次（`92-103`），第一轮结束后就有。
- **够不够算进度**：够。`total_rounds` 是已完成轮数，`attacks.length` 是当前攻击总数，另有 `claims.length`、`chains.length`、`token_estimates`、`evidence_pool_size`。分母用 sikeoop 自己传的 `--max-rounds`；但可能提前结束（2.5），进度条不能假设一定跑满。
- **要注意**：
  1. 写入不是原子的（直接 `open(…, 'w')` 覆盖，`102`），读的时候可能读到半个文件，要容错重试。
  2. 没指定编码（`102`），Windows 上按系统代码页写；见 5.3。
  3. 写失败没有 try，会让整场运行直接崩。
  4. 每次写都要重建摘要，而重建摘要在攻击 ≥ 5 条后会调一次 LLM（发现 G）。

### 3.2 stdout

全是 `print`，没有颜色码、没有进度条。可解析的行：

| 行 | 位置 |
|---|---|
| `-- Round N --`（N 从 0 起，表示这一轮开始） | `session.py:108` |
| `  [agent_i] calling <provider>/<model>...` | `content_layer.py:420` |
| `  [agent_i] → <action> <细节>`，或 `  [agent_i] call failed: <错误>` | `content_layer.py:484`、`438` |
| `  [Evidence] …` | `session.py:127-130`、`evidence_layer.py:405-438` |
| `  Claims:x Chains:y Attacks:z`（当轮有链或攻击才打印） | `session.py:439-440` |
| `  TERMINATED: <原因>` | `session.py:550` 等 |
| 结尾：`Rounds: N  Terminated: …`、`Tokens: …  Calls: …`、`Saved: <路径>` | `cli.py:93-109`、`83` |

适不适合作兜底：适合看“第几轮、谁在调用、谁失败了”，粒度比 checkpoint 细。两个前提：

- Python 的 stdout 接到管道时默认整块缓冲，要加 `-u` 或设 `PYTHONUNBUFFERED=1` 才是实时的（Python 自身行为，**未在此包内确认**）。
- 打印内容含 `→`、`≤`、中文和模型生成的文字，Windows 管道下的编码问题见 5.3。

另外 `call failed: <错误>` 会把 SDK 的报错原文打出来，里面可能带有打了码的 Key 片段（SDK 行为，**未确认**）；原始输出不宜直接落盘或展示。

### 4.2 除了改源码，能不能指定 base_url

- 包自己**没有**提供任何方式。`LLMConfig` 有 `base_url` 字段（`config.py:26`），OpenAI 兼容路径也会优先用它（`content_layer.py:209`、`224`），但 `Config.from_env()` 只按 `provider:model` 构造（`config.py:85`、`93`），没有环境变量、配置文件或命令行参数能给它赋值。`anthropic` 路径根本不看这个字段（`194`）。
- **可能的旁路（未确认，属于 SDK 行为，不在这个包里）**：
  - `openai` 这一家创建客户端时 `base_url=None`（`224`）。OpenAI 的 Python SDK 在这种情况下会读环境变量 `OPENAI_BASE_URL`。如果成立，用 `openai:<模型名>` + `OPENAI_API_KEY` + `OPENAI_BASE_URL` 就能接一个 OpenAI 兼容的中转站或自定义服务商。限制：所有 `openai:` 的 agent 共用同一个地址。
  - `anthropic` 的 SDK 同理可能读 `ANTHROPIC_BASE_URL`。
  - 其余 7 家显式传了地址，环境变量改不了。
  - 这两条需要在装好 SDK 的环境里实测一次才能写进方案。

### 4.3 缺 Key 时的表现

- Key 从环境变量取，取不到就是空串（`config.py:28-33`）。
- 构造配置、建 Session 时都不检查。到真正调用时才失败：异常在 `collect_round` 里被接住，打印 `call failed`，这个 agent 当轮记为 `pass`（`content_layer.py:432-445`），随后的重试也会因异常立刻放弃（`466-471`）。
- 结果：缺 Key 的模型每轮沉默，整场继续。所有 Key 都缺时，会空转到第 4 轮后以 `ALL_PASS_CONSECUTIVE` 结束，输出一份空结果。**不会以非零退出码报错。**
- provider 名字写错同样只是 `call failed`（`247-251`）。`CHAIN_CENTRIC_AGENTS` 里没有冒号的条目会被悄悄丢掉（`config.py:83`）；一个都不合法时退回单个 `anthropic` agent（`config.py:92`）。
- 包里有 `keys` 子命令，逐家打印 `SET` / `MISSING`（`cli.py:85-91`），不打印 Key 本身。它只看环境变量在不在，不验证 Key 是否有效。

结论：没有“代码用了但没声明”的依赖。`pip install <包目录>[llm]` 能装齐运行所需的全部（会顺带装上用不到的 scipy / pydantic / rich）。只用 OpenAI 兼容那几家的话，`anthropic` 可以不装。`windows_runner.py` 还用了标准库的 `tkinter`（`21-41`），sikeoop 不走这个文件。

### 5.2 Python 版本

`requires-python = ">=3.10"`（`pyproject.toml:10`）。这是真的需要：`cli.py:11` 和 `config.py:37`、`73` 在没有 `from __future__ import annotations` 的文件里用了 `str | None` 这类写法，3.9 会直接报错。

### 5.3 Windows 上的问题

| # | 问题 | 位置 | 后果 | 不改源码的办法 |
|---|---|---|---|---|
| 1 | `demo` 把结果写到 `/tmp/cc_demo_<场景>.json` | `cli.py:52-53` | Windows 上跑完才失败 | 不用 `demo`（方案已定只用 `run`） |
| 2 | 读 `.env` 没指定编码 | `config.py:9` | `.env` 是 UTF-8 且含中文时，import 阶段就可能报错 | 见下 |
| 3 | 写 checkpoint 没指定编码，内容含中文（`_symbol`、总结） | `session.py:102` | 系统代码页不是中文的 Windows 上，第 1 轮结束写 checkpoint 就可能崩；中文代码页下遇到模型输出的生僻字符也可能崩 | 见下 |
| 4 | 写主目录快照没指定编码 | `session.py:466` | 同上 | 见下 |
| 5 | 往 stdout 打印 `→`、`≤`、中文和模型文本 | `content_layer.py:481,484`、`session.py:242,267,468`、`cli.py:104-109` | 输出接管道时用系统代码页严格编码，遇到编不了的字符抛异常；发生在 `cli.py:77` 的话输出文件不会写 | 见下 |

第 2–5 条的共同办法：启动子进程时设 `PYTHONUTF8=1`（Python 的 UTF-8 模式，让默认文件编码和标准输出都用 UTF-8），sikeoop 这边按 UTF-8 读 checkpoint 和输出流。这是 Python 自身的机制，**在这个包上未实测**。

没发现的问题：没有用信号、没有 fork；路径都走 `os.path` / `pathlib`；`python -m chain_centric.cli run …` 可用（`cli.py:111-112`，包自带的 `run_custom_windows.bat:16` 就是这么调的）。

### 5.4 `.env` 的读取

- **时机**：`chain_centric.config` 被 import 时立刻执行（`config.py:17`），任何子命令都会触发。
- **顺序**：先 `<当前工作目录>/.env`，再 `~/.chain_centric.env`（`config.py:7`）。
- **优先级**：每个键只在环境里还没有时才写入（`config.py:15`）。所以：显式传入的环境变量 > 工作目录的 `.env` > 主目录的文件。**方案 3.3 的判断成立。**
- **格式**：`KEY=value`，去掉首尾引号；跳过空行和 `#` 开头的行；不支持 `export`；键名不去空格（`config.py:10-16`）。
- **要注意**：sikeoop 没传的 Key，仍会从用户的 `~/.chain_centric.env` 里补进来。也就是用户没在 sikeoop 里配的服务商，可能被悄悄用上、产生费用。要挡住它，可以把没用到的 Key 显式传成空串（空串算“已存在”，不会被文件覆盖；Windows 上空值环境变量能否传进子进程 **未确认**），或者见第 8 节改子进程的主目录。

## 6. 证据库（`-r`）

### 6.1 接受的格式

`cli.py:11-30`：文件必须存在（`cli.py:59`），按 UTF-8 读。

- 顶层是数组：直接用。
- 顶层是对象：按顺序找 `items` → `evidence` → `ccma_repository_items` → `repository_items` → `claims`，用第一个是数组的；都没有但对象自己带 `ref` / `title` / `detail` 之一，就当成单条记录。
- 其他情况报错退出。

每条记录（`evidence_layer.py:222-264`）：

| 字段 | 说明 |
|---|---|
| `ref` | 引用标识，模型引用证据时用它。普通记录缺省为空串；带 `claims` 的记录缺省自动生成 |
| `title` | 截到 200 字 |
| `detail` | 截到 500 字 |
| `source` | 缺省 `"repository"`，任意字符串 |
| `claims` | 可选数组，每项 `{title, detail}`。有它时，这条记录被拆成多条独立证据，ref 为 `<ref>/claim_<序号>`，标题为 `<记录标题> — <声明标题>` |

所有预载证据的核实级别都记为“已核实存在”（`242`、`261`）。超长内容是静默截断的。

另一个要知道的行为：建 Session 时会先扫一遍**问题文本**（`evidence_layer.py:272-335`，发生在载入证据库之前，`cli.py:74-75`）。问题里形如 `- 名称: 值` 的行会被当成“指标”证据，代码块会被当成“代码”证据，并且都标成最高的“已核实”级别；问题全文本身也作为一条证据入池。

## 7. 花费

### 7.1 每轮的 LLM 调用

设 agent 数为 N（方案里是 5）：

| 调用 | 次数 / 轮 | 用哪个模型 | 是否计入 `token_estimates.calls` | 位置 |
|---|---|---|---|---|
| 每个 agent 发言 | N（并发） | 各 agent | 是 | `content_layer.py:411-426` |
| 输出格式不对时重试 | 每个 agent 最多 +2 | 各 agent | **否** | `content_layer.py:450-471` |
| 证据搜索 | 0 或 1（第 1 轮起，触发条件很宽：焦点变了、近 2 轮有攻击、证据池不足 10 条等） | 证据模型 | 是 | `session.py:112-128`、`272-295` |
| agent 主动要证据 | 每个带 `need_evidence` 的攻击 +1，最多 N | 证据模型 | 是（沿用同一个计数器） | `session.py:157-166` |
| 新颖度判断 | 0 或 1（当轮有新链且已有旧链时） | 证据模型 | **否** | `session.py:413-417`、`914-958` |
| 攻击主题聚类 | 每次生成摘要 1 次，攻击 ≥ 5 条后才有。**开了 checkpoint 就是每轮 1 次**；另外结束时 1 次、语义快照 1 次 | 证据模型 | **否** | `session.py:874-912` |

粗算：每轮约 **N + 1 到 N + 3 次**，格式重试和主动要证据多的时候更高。按 5 个 agent：

| 轮数 | 大约调用次数 |
|---|---|
| 12 轮（包自带 bat 的默认值，`run_custom_windows.bat:16`） | 70–110 |
| 30 轮（`run` 的默认上限） | 180–270 |

它自己打印的 `Calls` 会偏低（三类不计数）。

### 7.2 单次调用的输入大小

agent 发言一次的输入（`content_layer.py:418`、`evidence_layer.py:443-521`）：

| 部分 | 大小 |
|---|---|
| 系统提示 | 约 1,230 字符（`content_layer.py:130-151`） |
| 两段格式模板 | 约 860 字符（`153-185`） |
| 问题全文 | 原样 |
| **整个证据池**，每条一行标题（至多约 180 字符）加一行 detail（至多 200 字符） | 每条至多约 400 字符 |
| 焦点命题（最多 3 条）、最近动态（最多 6 条） | 约 1,000 字符以内 |
| 针对自己的攻击（最多 5 条） | 约 1,500 字符以内 |
| 待审查的链（最多 8 条，每条 3 步） | 约 4,000 字符以内 |

证据池是大头，而且每轮可能再长最多 5 条（`evidence_layer.py:418`）。举例：

- 55 条证据的预设：单次输入约 2.5–3 万字符。
- 没有证据库的短问题：约 4,000–8,000 字符。

其他调用：证据搜索约 1,200 字符加最近 10 条证据标题；新颖度判断不超过约 5,500 字符；主题聚类不超过约 4,500 字符。输出上限都是 4,096 token。

确认卡上的说法建议写成区间，并说明“证据越多、轮数越多越贵”。包里没有 token 或金额上限，唯一的闸是轮数。

| 类别 | 事实 | 位置 | 建议 |
