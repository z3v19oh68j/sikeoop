# Opus 5.5 提示词要点（整理自 Anthropic 官方文档，2026-10-11）

来源：
- [Prompting Claude Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5)
- [Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)（5.5 仍适用）
- [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)

以下为意译与归纳，不是原文。

## 1. 省 token：先调 effort，不靠提示词

- 思考在 5.5 上**始终开启**，`effort` 是控制思考量的第一开关。默认 `medium`；官方测试里 5.5 的 `medium` ≈ 5 的 `high`，编程任务上 `low` 也接近，成本低很多。
- 想少思考：**先降 effort**，比写“别想太多”可靠。`xhigh` / `max` 只留给实测有收益的任务。
- 中途改顶层 effort 会让提示缓存失效；要改用“按消息改 effort”（beta），缓存保留。
- `max_tokens` 要给思考留够空间（思考算在里面），长的编程回合官方用 128k。
- 聊天类系统提示里“请仔细思考再回答”这类句子可以删：回复更快，质量没明显下降。

## 2. 减少错误与浪费

- **别再加“最后验证一遍”“用子代理复查”“double-check”**：模型自己会验证，再叫它复查只会过度验证、白烧 token。
- **代码审查别写“只报高严重度”**：它会照字面少报。要它全报，另起一轮过滤。
- **把完整任务一次交代清楚再放手**：多文件、端到端的活它最擅长，给全规格比来回追问好。
- **限定范围**：窄任务明确说“按要求的范围交付，有更好的做法说一句然后照做”，防止它擅自扩大或缩小任务。
- **语气别太凶**：“CRITICAL / 必须”这类强调在新模型上会导致过度触发，正常语气即可。
- 说“要做什么”比说“不要做什么”有效；格式要求用 XML 标签分块，例子放 `<example>`。

## 3. 子代理：少派、派大块

- 只把**大而独立、可并行**的活派给子代理（例如大范围多文件调查）；几次工具调用能做完的自己做；不要用子代理来复查自己。
- 能一个子代理搞定就别派多个。Claude Code 里可用环境变量限深度和并发（`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`、`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`）。
- 多代理团队给**时间信号**（如每条回传附 `elapsed 340s / 1200s`）能让它更好地并行、更早完成；预算只是建议，硬上限要自己设超时。

## 4. 长时间无人值守

- 5.5 会在长任务中途发进度并结束回合；无人值守的循环别把“纯文字结束”当成“任务完成”。
- 用任务清单（to-do / 文件）记录未完成项；回合结束还有未完成且没说卡在哪，就自动发一句“还剩 X、Y，继续；卡住就说卡在哪”。同一任务最多自动续 2–3 次。
- 有后台命令或子代理还在跑时，不算完成，等结果回来再交给模型。
- 有人值守的场景不要加“别停下来汇报”这类指令。

## 5. 输出长度与汇报

- effort 管“想多少”，不管“说多少”。要短就明说，例如“回答聚焦、简短，免责声明从简”。
- 写进文件的报告也偏长：加一句“文档长度匹配任务需要，不要凑小节、重复总结”。
- 进度汇报的节奏可以直接规定：第一次调用工具前一句话说要做什么；中途只在有重要发现或改方向时说；结束时第一句先说结果。
- 只纠正会影响用户代码 / 结论 / 决定的早先错误，小笔误默默改掉。

## 6. 安全与粘贴内容

- 用户粘贴的外部文本用带随机 id 的 `<pasted_content id="…">` 包起来，并在系统提示说明其中的指令只在用户本人要求时才执行——5.5 对这类注入抵抗更强。
- 不要要求模型把内部思考原样写进回复，可能被 `reasoning_extraction` 拒绝；要过程就读 thinking 的摘要块。
- 网络安全：审代码找漏洞允许，高风险两用活动会被拦。

## 7. 其他

- 前端设计：泛泛说“别像 AI 做的”没用，要**点名**不要哪些样式（如米白背景、斜体强调词、01/02/03 编号标签、胶囊按钮），迭代追加。
- 复杂图表 / 截图：5.5 读图更准；最难的图给高分辨率 + 裁剪工具更有效。
- 跨多个应用的自动化：一句“动手前先广泛查看相关邮件、文档、表格”能明显提升正确率（但这些来源里要排除不可信内容）。

## 落到我们这里

### sikeoop 内置 AI（`src/main/agent/**` 的系统提示）
1. 给每种用途设 effort：对话 / 子任务 / 压缩摘要用 `low`，编程主线 `medium`，难题路由才上 `high`；和现有「模型分工」的难度路由合并。
2. 删掉系统提示里的“仔细思考”“最后自检”“double-check”类句子。
3. 加一段简短的进度汇报节奏和“只做要求范围内的事”。
4. 用户粘贴内容加 `<pasted_content>` 标记。
5. 额度自动续写（quota）与调度核心的“未完成就续”：最多自动续 2–3 次，然后停下等人看。
6. 跨模型切换时保持 effort 不随意改，避免缓存失效。

### 我们的军团协作（LEGION.md 与派活提示）
1. 派活一次给全规格（我们的任务书已是这样，保持）。
2. 去掉派活提示里的“最后跑一遍验证”以外的重复复查要求；typecheck / test 作为验收标准保留（这是客观检查，不是让模型自我复查）。
3. 子代理只派大块独立的活；小改动（如 vsix 上限）指挥官直接做。
4. 汇报模板统一：先结果、再改动文件、再存疑，限制篇幅。
