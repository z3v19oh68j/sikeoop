# 性能优化：诊断与方案

日期：2026-10-12（2026-10-14 在新 main 上重做）　状态：P0、P1 已完成（第 8 节）；P2 待做
依据：源码审查＋实测（第 2 节）。路径均相对 `sweet-code-desktop/`。

## 1. 结论

卡顿主要来自渲染层，而且集中在四个地方。按实测影响从大到小：

| # | 卡在哪 | 实测 | 修完预期 |
|---|---|---|---|
| R1 | **流式输出代码块时，每来一个字就把整个代码块重新高亮一遍** | 2 万字的代码块：脚本 32.9 s、布局 16.3 s，424 帧超过 50 ms；本该 67 s 播完，实际拖到 146 s | 与不高亮的同一段一致：脚本 5.9 s、布局 4.4 s，1 帧超过 50 ms |
| R2 | **流式输出时，每来一个字就把整条回复重新解析成 Markdown** | 2 万字的说明文字：脚本 31 s，占界面线程约 41%；单次解析从 2k 字时的 2 ms 涨到 2 万字时的 22 ms | 只重解析最后一个没写完的段落：CPU 降到约 1/8 |
| R3 | **编辑器每敲一个键，整个应用都要重新渲染一遍** | 每键脚本 10.8–11.3 ms | 每键 4.4–5.6 ms（-50%，实验证实） |
| R4 | **看不见的页面也在后台刷新** | 调度台隐藏时，30 个运行中的任务每秒推 4 次快照，每次约 354 KB，占渲染层约 10% CPU | 隐藏时不刷新；快照不再带进度明细 |

另有两项启动问题：

- **S1**：主窗口要等登录 shell 读完环境变量才创建（`src/main/index.ts:2377`、`:2391`），最多等 5 秒。
- **S2**：渲染层入口包 6.85 MB，启动时一次性解析，最大的单个任务约 300 ms；首页已有 2500 个 DOM 节点，因为十几个页面都已挂载。

**实测不是瓶颈的**：终端渲染、长对话历史、调度台以外的隐藏页面（第 4 节）。这些先不动。

## 2. 测量方法

- **环境**：云端容器，无头 Chromium（Playwright 1.56）；渲染层用生产模式 React 构建，接 `dev-mock`。Electron 主进程没有实测：容器里没有 Electron 二进制，`node-pty` 也编译不了。主进程的结论来自读代码。
- **注入方式**：在页面加载前接管 `window.sweet.onAgentEvent`、`onTermData` 和 `onDispatchChanged`，按真实节奏推送事件：每 20 ms 一个 6 字的增量（每秒 50 次）；终端每秒重绘 25 次状态行，每秒再输出一段 40 行。
- **指标**：
  - 来自 CDP `Performance.getMetrics`：脚本、布局、样式时间；
  - 来自 PerformanceObserver：长任务（超过 50 ms）；
  - 来自 requestAnimationFrame：帧间隔；
  - Markdown 解析成本另用 Node 单独测（`react-dom/server` ＋ 和 `Markdown.tsx` 相同的插件）。
- **口径**：绝对数值取决于机器，用户的电脑上可能更慢。**对比数值**（修前和修后、有高亮和无高亮）可以直接参考。
- 测试脚本都放在会话的 scratchpad 里，没有进仓库；第 6 节建议把它们收进仓库，作为性能基线。

## 3. 发现与修法

### R1　代码块流式高亮（最严重）

**根因**

- `src/renderer/src/components/Markdown.tsx:223-238` 的 `useHighlighted(code, language)` 以 `code` 为依赖。流式输出时，代码块每多一个字 `code` 就变一次，于是每次都调 `monaco.editor.colorize` 把整块重新着色（`src/renderer/src/languages.ts:143-153`）。
- 返回的 HTML 再整块替换进 DOM，造成大量布局计算。
- 缓存的键是「整段代码」，流式过程中的每个前缀都是一个新键，会把有用的缓存（上限 200 条，`languages.ts:137`）挤掉。

**实测**（同一段 2 万字、150 行的 TypeScript 代码块）：

| | 脚本 | 布局 | 实际播放时长 | 长任务 | 超过 50 ms 的帧 | p95 帧 |
|---|---|---|---|---|---|---|
| 现状（高亮） | 32.9 s | 16.3 s | 146 s | 136 | 424 | 67 ms |
| 同一段按 plaintext（不高亮） | 5.9 s | 4.4 s | 69 s | 2 | 1 | 17 ms |

**修法**

1. 代码块的围栏还没闭合（还在流式输出）时，不着色，显示纯文本；闭合后着色一次。
2. 闭合后内容如果仍在变，就等内容停止变化 200 ms 后再着色，作为兜底。
3. 不往缓存里放未闭合代码块的结果。

**负责**：Claude 军团（`Markdown.tsx`、`languages.ts`）。

---

### R2　流式 Markdown 整段重解析

**根因**

- `Markdown.tsx:23-24` 的注释写明了「Re-parsed on every streamed delta」。
- `src/renderer/src/components/ChatPanel.tsx:186-190` 每收到一个 `text_delta` 就 `setTurns` 一次，正在输出的那条回复每次都整段重新解析。
- 同时 `:195-198` 每次都读 `scrollHeight`，强制做一次布局。

**实测**

| 场景 | 结果 |
|---|---|
| Node 单次解析＋渲染 | 1k 字 2.6 ms、5k 字 8.3 ms、1 万字 11.8 ms、2 万字 22.1 ms |
| 1 万字的回复，按 6 字一个增量流式输出（1666 次） | 整段重解析共 7.8 s CPU，最差一次 18.9 ms |
| 同上，只重解析最后一个未完成的段落 | 共 0.9 s，最差 4.8 ms |
| 浏览器内：2 万字说明文字流式输出 | 脚本 31 s / 76 s。本机还没出现长任务，但 CPU 已被占掉四成，在慢一些的笔记本或更快的输出速度下就会掉帧 |

**修法**

1. **合批**：`ChatPanel` 收到的 `text_delta` 和 `thinking_delta` 先攒在 ref 里，每个动画帧（`requestAnimationFrame`）才 `setTurns` 一次。增量速度通常是每秒 30–100 次，合批后最多每秒 60 次，突发的多次增量合成一次。
2. **分块**：把正在输出的文本按「块」切开，切的时候要识别代码围栏，围栏内的空行不能切。已经写完的块各自用 `memo` 的 `<Markdown>` 渲染，不再变化；只有最后一个未写完的块每次重解析。回复结束后再整段解析一次，保证最终渲染和现在完全一致（跨块的引用式链接、脚注等）。
3. **自动滚动**：自动滚动的检查也放进同一个动画帧里做。

**负责**：Claude 军团（`ChatPanel.tsx`、`Markdown.tsx`）。

### R3　编辑器每键触发整个应用重渲染

**根因**

- `src/renderer/src/App.tsx:899-904`：编辑器的 `onChange` 每次都调用 `setFiles`。`files` 是 App 级状态，于是每敲一个键，整个 App 都重新渲染。
- App 下面挂着十几个始终存在的页面（`App.tsx:745-826`），都没有 `memo`，全部跟着重渲染。
- `onSelection={setSelection}`（`:906`）在拖选文字时也会触发同样的重渲染。

**实测**（每键脚本时间，打 100 个字）：

| | 对话 1 轮 | 对话 64 轮 |
|---|---|---|
| 现状 | 10.75 ms | 11.34 ms |
| 实验：去掉每键的 `setFiles` | 5.58 ms | 4.37 ms |

实验只是临时注释掉一行、量完就恢复了，没有提交。

**修法**

1. 文件内容的唯一来源改成 Monaco 的 model 和 `filesRef`。React 状态只在「是否有未保存改动」翻转时更新（第一次改动、保存、撤回到原样）。
2. 用到文件内容的地方（保存、提交给 AI 的编辑器上下文）都从 ref 或 model 读，不从 state 读。
3. 选区改为只在用户停下来约 150 ms 后才更新到 App；或者由 `ChatPanel` 在发送时自己读，不再进 App 状态。
4. 重的页面组件包一层 `memo`，并把传给它们的回调改成稳定的引用。这一步也是 R4 的前提。

**负责**：Claude 军团（`App.tsx`、`EditorPane.tsx`）。

### R4　隐藏页面在后台刷新；调度台快照过大

**根因**

- 十几个页面只用 `hidden` 属性藏起来（`App.tsx:745-826`），组件始终挂载，订阅和定时器一直在跑。
- 调度台尤其明显：
  - 隐藏时照样订阅（`src/renderer/src/components/DispatchConsole.tsx:141-153`）；
  - 只要有任务在跑，就每秒重渲染一次（`:158-163`）；
  - 主进程每 250 ms 推一次完整快照（`src/main/index.ts:384-390`），里面带着最多 200 个任务和每个任务的 100 条进度、完整输入。
- 主进程那边，每个进度事件还会追加整条任务日志（见 [#1](https://github.com/z3v19oh68j/sikeoop/issues/1) 的 F3）。

**实测**：30 个运行中的任务、170 条历史，每 250 ms 推一次快照：

- 单个快照约 354 KB（JSON）；
- 调度台隐藏时，渲染层每 10 秒花 1.0 s 脚本时间（约 10%）；
- 这还不算主进程序列化约 1.4 MB/s 和渲染层反序列化的开销。

**修法**

1. **渲染层**：
   - 重的页面在隐藏时停掉订阅和定时器：调度台、集群、回归、群聊、自动化、用量、手机、扩展等。
   - 这些页面也可以干脆在隐藏时卸载，把状态放到外层；
   - 再配合 R3 的 `memo`。
2. **主进程**：
   - 只在调度台可见时推送完整快照；不可见时只推运行数、排队数这类摘要。
   - 快照里去掉 `progress`，输入只留前 200 字；展开某个任务时再按需取它的进度（新增 `dispatch:job(id)`）。
3. 与 #1 的 F3 一起修：进度事件不再触发整条任务的事件和日志写入。

**负责**：Claude 军团（各页面组件）；Codex（`index.ts` 的推送逻辑、新 IPC）；指挥官（`DispatchView` 类型和 preload 接口）。

### S1　启动等待 shell 环境

**根因**

- `src/main/index.ts:2377` 先 `await Promise.all([… loadShellEnv() …])`，再到 `:2391` 才 `createWindow()`。
- `loadShellEnv`（`src/main/shell-env.ts:18-47`）会启动一个交互式登录 shell（`-ilc`），超时 5 秒。macOS 上装了 oh-my-zsh、nvm 的用户，通常要等 0.5–3 秒，窗口这段时间都出不来。
- `research.init()`（`:2379`）也在窗口创建之前被等待。

**修法**

1. 先 `createWindow()`。
2. `loadShellEnv()` 改为后台进行，并保存成一个 Promise；只在真正需要 PATH 的地方 `await` 它：MCP 加载、终端和 CLI 启动、执行命令、`findBash`。
3. `research.init()` 改到首次使用时再执行。它本来就有 `??=` 惰性初始化（`src/main/research/runner.ts:34`），启动时可以不调。

**负责**：Codex（`index.ts` 启动段、`shell-env.ts`）。

**风险**：要逐个检查依赖 PATH 的入口都先等到了环境，否则会出现「找不到 node / npx」。

### S2　入口包过大、页面全部预先挂载

**实测**

| 项 | 数值 |
|---|---|
| 入口 chunk | 6.85 MB（Monaco、three.js、xterm 和所有页面都在里面），JS 合计 20.8 MB（含 worker） |
| 冷启动到首页可用 | 约 1.2 s（本机） |
| 最大的单个任务 | 约 300–345 ms |
| DOM 节点 | 首页 2500 个，打开项目后 3460 个 |

**修法**

1. 低频页面改用 `React.lazy` 按需加载：工作室、图谱、Wiki、论文、PV、科研、回归、工具箱、手机、遥控、扩展、用量、自动化、群聊、集群、调度台，以及用到 three.js 的首页伙伴页。
2. Monaco 推迟到第一次打开文件时再加载：`main.tsx:2` 现在一启动就静态导入 `./monaco`；聊天里的代码高亮也改为等 Monaco 加载后再着色。
3. 隐藏页面按需挂载：第一次打开时才挂载，之后用 `hidden` 保留状态。这样既保留切回来时的状态，启动时也不必一次全建好。
4. （待验证）渲染层改由自定义协议加载，并开启 V8 代码缓存，让重复启动不必每次重新编译。需要先确认 Electron 44 的 `protocol.registerSchemesAsPrivileged` 是否支持 `codeCache`。

**负责**：Claude 军团（`App.tsx`、`main.tsx`、`monaco.ts`）；第 4 步由 Codex 负责。

**验收**：入口 chunk 小于 3 MB；首页 DOM 节点少于 1200；冷启动最大单任务小于 150 ms。目标值以第一次拆分后的实测为准，再定稿。

## 4. 实测不是瓶颈的（暂不处理）

| 怀疑点 | 实测 | 结论 |
