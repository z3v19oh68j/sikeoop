# 代码地图：方案

日期：2026-10-11　状态：待用户确认（第 7 节）
依据：源码侦察（只读）＋ 本仓库上的原型测量（附录 A）。路径均相对 `sweet-code-desktop/`。

## 1. 问题

大模型每接手一个工作区，都要先花大量轮次摸清「哪块功能在哪」。现在能帮它定位的东西有四样，但都不是地图：

| 现有机制 | 位置 | 不足 |
|---|---|---|
| 项目概览 | `src/main/agent/context.ts:8-15`，对话开头发一次 | 只有文件树，4 层深、最多 300 行，大项目会被截断；只有文件名，不知道每个文件是干什么的 |
| 自动附带的代码 | `src/main/hooks/builtin/rag.ts` | 每条消息最多 3 段，跟着当前这句话走，不是全局视图 |
| `search_code` 工具 | `src/main/tools/context-tools.ts:21` | 要先猜关键词，一轮一轮地搜 |
| 项目 Wiki | `src/main/wiki/service.ts` | 写给人看的，不会交给模型；要先手动生成 |

结果有三个：

- 大项目上，模型的前几轮都在 `list_files`、`search_code`、`read_file` 之间来回。本次调度审查里，光是找到 `dispatch/` 下各模块和各个入口，就用了十几次搜索和读取。
- 派出去的子代理更惨：模型子代理、集群角色、终端里的 Claude Code / Codex 都从零开始，各自再摸一遍。并行派活越多，这份重复成本就越高。
- 每次重新摸索也容易漏：只看到一个入口，就以为找全了。

## 2. 目标与非目标

**目标**

1. 对话一开始，模型就知道项目分成哪几个功能区、每个区在哪、是干什么的。
2. 需要细节时，一次调用就能看到某个区里每个文件的用途和主要符号（带行号）。
3. 地图随代码变化自动更新，不用手动维护。
4. 主对话、子代理和终端 CLI 会话共用同一份地图。
5. 基础版不依赖模型，离线可用，生成成本几乎为零。

**非目标**

- 不取代 `search_code`、`read_file`：地图负责「去哪找」，读代码还是靠它们。
- 不做调用图或类型分析，以后需要再说。
- 不往用户的项目里写文件。导出 `CODEMAP.md` 只在用户自己点按钮时才做。

## 3. 设计

### 3.1 三层地图

| 层 | 内容 | 大小 | 何时给模型 |
|---|---|---|---|
| **L0 区域总览** | 功能区名称、一句话用途、所在目录、文件数 | ≤ 6000 字符（约 2k token） | 每次对话开头，放进 `<project>`，替换现在的「文件结构（部分）」 |
| **L1 区域详情** | 区内每个文件：行数、头注释里的一句用途、导出符号及其行号 | 每区 ≤ 8000 字符 | 模型调用 `code_map` 工具时按需返回 |
| **L2 源码** | 原文 | — | 现有的 `read_file`、`search_code` |

只做 L0 不够：模型只知道「调度在 `dispatch/`」，还是要逐个打开文件。全量 L1 又太贵：本仓库约 17k token（附录 A），每次对话都带上不划算。所以采用「总览常驻、详情按需」。

```

- src/main/dispatch/（10）调度核心：所有「把任务交给一个智能体」都经过这里
- src/main/rag/（4）项目代码索引：关键词＋语义检索
```

### 3.2 文件大纲：L1 的数据来源（确定性，不调模型）

1. **挂在代码索引上**：`CodeIndex.indexFile()` 读文件时顺手提取大纲，存进 `FileEntry`。
   - 好处是复用代码索引已有的扫描规则：遵守 `.gitignore`，跳过 `.env` 和密钥文件，最多 5000 个文件（`src/main/rag/code-index.ts:15-33`、`:131-160`）。哪些文件算代码，只有一处说了算。
   - 新鲜度也复用：代码索引每次查询前，都会按修改时间和大小重新扫一遍变化的文件。
2. **按语言提取**，规则用一张表配置，后续加语言只改表：

   | 语言 | 一句用途从哪来 | 符号 |
   |---|---|---|
   | TS / JS / ArkTS（`.ets`） | import 之后的第一段注释 | 顶层 `export` 的 class / function / const / interface / type / enum；ArkTS 另取 `@Component struct` |
   | Python | 模块 docstring | 顶层 `def`、`class` |
   | Go | package 注释 | 导出（首字母大写）的 `func` 和 `type` |
   | Rust | `//!` 文档 | `pub fn`、`pub struct`、`pub enum`、`pub trait` |
   | Java / Kotlin / Swift | 文件第一段注释 | 顶层 `class`、`interface`、`object`、`struct`、`func` |
   | Vue / Svelte | 第一段注释 | 组件名，以及 `<script>` 里的导出 |
   | Markdown | 第一个标题 | 二级标题 |
   | 其他 | 第一行非空内容 | 无 |

3. **截断**：一句用途最多 80 字；每个文件最多列 12 个符号。用途文本先过 `src/main/memory/redact.ts`，抹掉可能写在注释里的密钥。

### 3.3 功能分区：L0 怎么划区

**目录分区**（默认，确定性）

1. 从根目录往下走。一个目录的子树里如果有 3 到 40 个代码文件，它就成为一个区；超过 40 个就继续往下拆；直接放在被拆目录里的文件，单独归成「`<目录>/` 根文件」区。
2. 区的总数超过 60 时，合并文件最少的兄弟目录。
3. 用途按以下顺序取第一个有的：该目录的 README 第一句 → `index.*`、`main.*` 或与目录同名文件的头注释 → 区内最大文件的头注释。

**模型分区**（可选增强）

1. 输入：目录清单＋每个文件的一句用途。本仓库约 2.4 万字符，约 8k token。输出 JSON：`[{ name, purpose, paths[] }]`。
2. 用「模型路由」里的「子任务」模型，一个项目只调一次。按目录结构的签名缓存；新增目录超过 10%，或者用户点「重新分区」，才会重做。
3. 校验：`paths` 必须真实存在；文件按「最长路径前缀」归入唯一一个区；归不进去的计入「未归类」。
4. 如果项目已经生成过 Wiki，并且 Wiki 没过期，就直接用 Wiki 的页面目录（每页的标题和文件清单）当分区，不再额外调模型。

### 3.4 新鲜度

- **L1**：每次调用 `code_map` 前，先触发一次代码索引的增量扫描（最多每 3 秒一次，沿用 `RESCAN_MS`），所以模型自己刚写的文件也能马上看到。
- **L0**：区的划分只在重新分区时才变。新出现的文件按前缀归入已有的区；归不进去的，在 L0 末尾提示「另有 N 个文件未归类」。
- **对话中途**：L0 只在对话开头发一次；历史被压缩后，会随项目概览一起重发（`src/main/agent/loop.ts:683-701` 现有的逻辑）。

### 3.5 交给谁、怎么给

| 使用方 | 方式 | 改动点 |
|---|---|---|
| 主对话 | L0 放进 `<project>`；提供 `code_map` 工具 | `agent/context.ts:8-15`、`tools/context-tools.ts`、`agent/prompts.ts:60` |
| 自动化的 agent 步骤 | 和主对话相同（同一个 `makeAdapter`） | 不需要额外改动 |
| 模型子代理、集群角色 | 第一条消息带上 L0；任务写了 `owns` 时，再附上 `owns` 涉及的区的 L1 | `index.ts` 的 `runWorkerSession`、`runRoleSession` |
| 终端里的 Claude Code / Codex | sikeoop 的 MCP 服务器增加 `code_map` 工具；`peerPrompt` 里加一句「不知道代码在哪，先用 code_map」；派活时在 `hostFraming` 里附一行相关区 | `peers.ts` 的 `TOOLS`、`rpc()`、`peerPrompt()` |
| 跨项目 session 成员 | 同上，但只能查本 session 的 roots | `peers.ts` ＋ `session/scope.ts` 的 `checkScope` |
| 用户 | 「上下文中心」查看地图，可以重新分区、开关功能、导出 `CODEMAP.md` | `ContextCenter.tsx`、设置 |

走 MCP 的原因：终端 CLI 会话不需要我们往项目里写文件，就能拿到和主对话同一份、实时的地图。

### 3.6 `code_map` 工具

- **参数**：`{ area?: string; path?: string }`
  - 不传参数：返回 L0；
  - `area`：区的名称或目录，返回这个区的 L1；
  - `path`：目录就返回该目录的 L1，文件就返回该文件的大纲。
- **属性**：只读，`permission: "auto"`，`parallelSafe: true`，结果最多 8000 字符，超出时提示改用更小的范围。
- **提示词**：把 `agent/prompts.ts:60` 改成：「不知道代码在哪里时，先看 `<project>` 里的代码地图找到功能区，用 code_map 看这个区的文件和符号，再 read_file；地图里找不到的，再用 search_code 按关键词搜。」

### 3.7 预算与降级

| 情况 | 处理 |
|---|---|
| L0 超过 6000 字符 | 先把子区折叠成父目录，再省略文件最少的区，并提示用 `code_map` 查看 |
| 项目文件超过 5000 个（索引被截断） | L0 标注「只覆盖了前 5000 个文件」 |
| 小项目（不到 4 个文件）或没开项目 | 保留现在的文件树 |
| 设置里关掉了代码地图 | 恢复现在的文件树，不提供 `code_map` 工具 |
| 模型分区失败 | 退回目录分区，并在上下文中心显示原因 |

### 3.8 隐私与安全

- 文件范围和代码索引完全一致，密钥文件本来就被排除；用途文本还会再过一遍 `redact.ts`。
- 模型分区只发送路径和每个文件的一句用途，发给用户配置的子任务模型，和平时对话的信任边界相同。用本地 Ollama 时，数据不离开电脑。功能关闭时不发送。
- MCP 的 `code_map` 只能查调用方会话所在的 root。`path` 先解析成真实路径，再检查是否在范围内，越界的请求一律拒绝。

## 6. 验收

**正确性**（`node --test test/codemap/`）

1. 每种语言至少一个夹具文件，用途和符号（含行号）都提取正确。
2. 分区的不变式：每个文件恰好属于一个区；区的数量 ≤ 60；L0 ≤ 6000 字符；每个 L1 ≤ 8000 字符。
3. 增量更新：改一个文件，下一次 `code_map` 就能看到新符号；新目录计入「未归类」。
4. 安全：`.env` 和密钥文件不出现在地图里；MCP 的 `code_map` 查 root 之外的路径会被拒绝。
5. `npm run typecheck` 没有新增错误。

**效率**：用附录 B 的 10 道定位题做对照实验。同一个模型，分别关闭和打开代码地图，各跑一遍。

- 指标：从提问到第一次 `read_file` 正确文件之间的工具调用次数，以及这段时间的输入 token（取自用量账本）。
- 目标（待确认）：工具调用次数的中位数 ≤ 2；输入 token 减少 40% 以上。
- 结果写进汇报，附原始数据。

## 附录 A　原型测量

在 scratchpad 里用一个一次性脚本，扫描 `sweet-code-desktop/` 下的 TS / JS 文件（跳过 `node_modules`、`resources` 等目录），提取每个文件的头注释和顶层 `export` 符号：

| 项 | 数值 |
|---|---|
| 文件数 | 437 |
| 有头注释的文件 | 281（64%） |
| 目录数 | 78；仅目录清单约 1.8k 字符 |
| 全量大纲（L1 全部） | 约 54.5k 字符，约 17k token |
| 单个区的 L1（`src/main/dispatch/`，10 个文件） | 约 1.9k 字符 |

结论：全量大纲太大，不适合常驻；按区下钻每次只要 2k 字符左右，适合「总览常驻、详情按需」。本仓库的头注释覆盖率高，目录分区的用途质量会比较好；注释少的项目，更值得用模型分区。
