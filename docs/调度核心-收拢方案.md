# 多智能体调度核心：收拢方案

日期：2026-10-10　状态：D1–D5 按建议通过；P0–P5 全部完成（P4 由终端 Claude Code 完成，P5 界面由 Claude 军团完成）；统一审批路由按用户 10-10 决定暂缓
依据：侦察报告（2026-10-10，只读）＋两周按 LEGION 调度子代理的实际痛点。路径均相对 `sweet-code-desktop/`。

## 1. 现状一句话

现在有 **5 套在跑的调度**（PeerBus 终端互发、主控 agent-bus 工具、鸿蒙集群 `dispatch_agent`、自动化状态机、群聊）＋ **2 套半成品**（跨项目 session、回归面板 Regress）＋ **2 条审批通道**（PeerBus ask、Approver）。它们各有一套状态枚举（至少 5 种）、循环上限（MAX_HOPS=5 / MAX_VISITS=30 / 删工具）、超时和持久化，互不相通。

最要紧的 4 个事实问题：
1. **文件锁只管 PeerBus 里的 Claude**，Codex、主对话、集群角色、自动化并行写同一文件没有互斥（`peers.ts:329-339`）。
2. **`start_agent` / `send_to_agent` 标了 confirm 却不出审批卡**（`tools/agent-bus-tools.ts:54,80`），自动化、微信等无人值守链路能直接驱动 CLI。
3. **PeerBus 派活不排队**，对方正在干活也直接往终端注入；用户任意按键就把跳数清零（`peers.ts:154`）。
4. **跨项目 session 卡在一半**：零件（`scope.ts`、`store.ts`、`buildSessionLaunch`、`onSessionEvent`）写好没接线，`SweetApi.session` 必填但 preload / dev-mock 未实现，导致 `npm run typecheck` 失败（指挥官已实测确认）。

## 2. 目标

一个调度核心 `src/main/dispatch/`，所有“把一件事交给一个智能体去做”的地方都经过它。现有 7 个模块变成它的**入口**（谁发起）或**执行体**（谁来干），不再各自实现排队、限权、状态和回收。

## 3. 核心设计

### 3.1 三种执行体（Executor）

| 执行体 | 包装的现有代码 | 用于 |
|---|---|---|
| `cli` | PeerBus + terminal（Claude Code / Codex 终端会话） | agent-bus、跨项目 session、Regress、LEGION |
| `session` | sikeoop 自己的 `AgentSession` | 鸿蒙集群角色、自动化 agent 步骤 |
| `model` | 一次性流式模型调用 | 群聊成员 |

统一接口：`start()`、`deliver(task)`、`cancel()`、`status`、`collect()`（取结果）。

### 3.2 统一任务模型 `Job`

```ts
interface Job {
  id: string; parentId?: string;            // 任务树：谁派生了谁
  origin: "user" | "chat" | "automation" | "cluster" | "session" | "wechat";
  executor: { kind: "cli" | "session" | "model"; ref: string };
  input: string;
  scope: { roots: string[]; owns?: string[] };   // 可写范围 + 文件归属
  limits: { timeoutMs: number; budget: number };  // budget 取代 MAX_HOPS / MAX_VISITS
  status: "queued" | "starting" | "running" | "waiting_approval"
        | "done" | "failed" | "cancelled" | "timeout" | "exited";
  result?: { text: string; envelope?: unknown; outcome?: string };
  checks?: CheckResult[];                       // 自动验收结果（3.5）
}
```

现有 5 套状态枚举都映射到这一套；各界面先做映射，不强迫一次改完。

### 3.3 调度器

- **每个执行体一条队列**：对方忙时排队，空闲（Stop / turn-complete）再投递。取消“忙时直接注入”。
- **全局并发上限**（默认 4，对应 LEGION）。
- **预算按任务树计**：子任务消耗父任务的预算，用完产生 `budget_exhausted` 事件等用户。只有用户的**真实发言（回车提交）**补充预算，不再是任意按键。
- **级联取消**：取消父任务会取消整棵子树。

### 3.4 守卫（Guard）

- **一个全局 FileLocks**：PeerBus 的 Claude hook、sikeoop 自己的写文件工具（`edit-tools.ts`）、集群和自动化都用同一个实例。
- **文件归属强制**：Job 带 `owns` 时，Claude 通过 PreToolUse hook 直接拒绝；`AgentSession` 在工具层拒绝；**Codex 没有前置 hook，只能事后检测**（见 3.5）。
- **派活前环境检查（preflight）**：目标目录能否写、是否需要网络、依赖是否已装，不满足就不派，直接告诉指挥官原因。（痛点：B3/B5 因工作目录和断网白跑一轮。）
- **统一审批路由**：PeerBus ask 和 agent-bus 都走一个审批路由（灵动岛 / 微信），统一 id 前缀、超时和排队；`start_agent` / `send_to_agent` 真正调用 `requestApproval`。Approver（外部 Claude 的全局 hook）保留为独立入口，但接入同一个路由。

### 3.5 自动验收（Verifier）

任务结束时自动执行，结果写进 `job.checks`：
- **改动范围**：任务前后对 `scope.roots` 做文件快照对比，列出改了哪些文件，超出 `owns` 的标红（这也是 Codex 越界的事后检测手段）。
- **类型检查增量**：派活前记录基线错误，结束后只报**新增**错误。（痛点：`session` 那个已有错误让每个子代理都得说明“忽略它”。）
- **汇报与事实对照**：汇报里声称新建的文件是否真的存在。

### 3.6 可观测与持久化

- 一条事件流 `dispatch:event` ＋ 快照 `dispatch:changed`。
- 每个项目一个任务日志 `userData/dispatch/<sha16(root)>/jobs.jsonl`（沿用现有的原子写惯例）；重启后把运行中的任务标为 `exited`。
- 一个统一的**调度台**界面：任务树、状态、日志、验收结果、取消按钮。合并现有的 ClusterConsole，以及终端面板里的智能体状态。

### 3.7 接口变更提醒

Job 可以引用接口文档（如 `docs/xxx.md` 第 N 节）并记录内容哈希。派活后文档有变化时，通知相关任务和指挥官。（痛点：任务清单第 1 节和代码对不上，要等 Codex 发现。）
