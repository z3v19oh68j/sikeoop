# 方案：sikeoop 与其他 AI agent 互相传任务（“打洞”）

日期：2026-10-11　状态：待用户确认　作者：终端 Claude Code（只出方案，没有改代码、没有改任何工具的配置）
路径均相对 `sweet-code-desktop/`。

## 0. 结论

1. **sikeoop 当中转站，不让 agent 之间直连。** 任何一次“把活交给另一个 agent”都变成调度核心里的一个任务（Job）。这样排队、次数上限、审批、验收、取消只有一套，已经写好的都能直接用。
2. **出站（sikeoop 派给外部 agent）首选 ACP。** ACP 是一套各家通用的协议，一个连接器能覆盖 opencode、CodeBuddy、Kimi 等多个工具；它走子进程的标准输入输出，不开端口；对方要权限时会发请求过来，正好接到 sikeoop 的审批卡上。opencode 是第一个落地对象。
3. **入站（外部 agent 派给 sikeoop 或别的 agent）沿用现有的 MCP 服务，加四个任务工具。** 现在只有 `send_to`（发一段话），要补成能提交任务、查进度、取结果、取消。
4. **调度核心新增一种执行体 `agent`**，不复用 `cli`。`cli` 是“往终端里打字”，`agent` 是“通过结构化接口对话”，两者的就绪判断、进度、权限处理都不一样。
5. **分五批**。第零批先做一次小实验（要实际启动 opencode，需要用户点头），把下面标了“未验证”的三个关键问题弄清楚，再决定第一批走 ACP 还是走 opencode 自己的 HTTP 服务。

需要用户拍板的事有 7 件，见第 9 节。

## 1. 现状：已经有什么，缺什么

### 已经有的

| 能力 | 在哪里 | 说明 |
| --- | --- | --- |
| sikeoop 派活给终端里的 Claude Code / Codex / 扩展 CLI | `dispatch/cli.ts`、`peers.ts` | 对方空闲时把任务当成一段话打进它的终端，它这一轮的最后一句回复就是结果 |
| 终端里的 agent 互相发消息 | `peers.ts` 的 MCP 服务（`list_peers`、`send_to`） | 只监听本机，每个会话一个随机令牌；消息上限 4000 字；经过调度核心排队和计数 |
| 接入别的 CLI | `cli-agents/`、`docs/cli-扩展开发文档.md` | 一个 JSON 定义；opencode 是内置的，带一个插件上报每轮开始结束，并在每次调用工具前问 sikeoop |
| 排队、次数上限、级联取消 | `dispatch/scheduler.ts` | 每棵任务树有预算（agent 发起的是 5 次，用户发起的是 20 次） |
| 派活前检查、写文件归属 | `dispatch/guard.ts` | 目录能不能写、要不要联网、这个文件归不归它 |
| 自动验收 | `dispatch/verify.ts` | 任务前后给目录拍快照，量出改了哪些文件；越界改动、新增类型错误、汇报里提到却不存在的文件 |
| 审批卡 | 灵动岛（PeerBus ask）、Approver | Claude Code 的权限请求能上卡；`start_agent` / `send_to_agent` 会先问 |
| 换模型时的上下文交接 | `agent/handoff.ts` | 把对话历史整理成一份可读记录，读过的文件内容原样带上，放不下时从最旧的开始省略 |

### 缺的

1. **往终端打字这条路太脆。** 没有结构化进度；结果只有最后一句话；opencode 要权限时只能提示“等你在终端里批准”，上不了审批卡；没有“改动文件清单”回传给派活的一方。
2. **只有 sikeoop 自己启动的会话能参与。** 用户在别处开着的 agent（自己的终端、IDE 里）进不来。
3. **agent 只能给同伴发话，不能把活交给 sikeoop 本身**，也拿不到任务编号，没法查进度、取结果、取消。
4. **跨工具没有上下文交接。** 每个接手的 agent 都要把文件重读一遍。
5. **扩展 CLI 没有沙盒也没有权限规则**（文档第 11 节写明了），全靠它自己的配置。

## 3. 六种接入方式对比

| 方式 | 怎么工作 | 优点 | 缺点 | 适合谁 |
| --- | --- | --- | --- | --- |
| **终端里打字**（现有） | 把任务打进对方的终端界面 | 已经做好；用户能看着它干活、随时插手 | 进度和结果靠猜；权限只能在终端里点；界面一改就坏 | 用户想盯着看的交互式会话 |
| **命令行一次性调用** | 每个任务起一个进程，读它输出的事件流 | 最简单，几乎每个工具都有；取消就是杀进程 | 权限没法来回问，只能事先定死或全放开；每次冷启动；续接要靠各家自己的会话参数 | 没有别的接口的工具（Aider、Cursor CLI）；无人值守的小任务 |
| **常驻 HTTP 服务** | 起一个服务，通过接口建会话、发消息、听事件 | 进度、中止、权限答复、改动清单都有；用户还能用界面连上去看 | 各家接口不一样，要一家一家写；要管端口、密码和进程生死；接口随版本变 | opencode、CodeBuddy 各自的专属能力 |
| **MCP** | 一方提供工具，另一方的模型来调用 | 几乎所有 agent 都能当客户端；sikeoop 已经有服务 | 它是“调用工具”，不是“交办任务”：没有任务生命周期、进度、取消，要自己在工具层面补 | **入站**：外部 agent 找 sikeoop |
| **ACP** | sikeoop 起对方的子进程，按统一协议建会话、发任务、收进度、答复权限、取消 | 一套代码覆盖多家；不开端口；权限请求是协议的一部分；进度是结构化的 | 协议还在演进，各家支持的深浅不一；不是每家都有 | **出站**：opencode、CodeBuddy、Kimi 等 |
| **A2A** | 通过网络发现对方的“名片”，用标准任务接口互派 | 为跨机器、跨组织设计；任务状态和产物的定义很完整 | 本机这些命令行工具都不原生支持；要开网络服务和做身份认证，对本机场景太重 | 将来的云端接单（`docs/方案-云端接单.md`） |
| **文件 / 队列信箱** | 往约定的文件夹里放任务文件，对方轮询取走，结果写回另一个文件 | 不需要任何协议；重启不丢；留痕；什么工具都能用 | 靠轮询，没有实时进度；取消只能靠约定；谁能写这个文件夹谁就能派活；要靠提示词让对方遵守 | 兜底；以及存放交接包、结果报告这类“内容” |

**取舍**：

- 出站用 ACP 做主干，一次性调用做兜底，终端打字保留给用户想看着的场合。
- 入站用 MCP。
- 文件只用来放内容（交接包、报告），不用来做控制。
- A2A 现在不做，但任务格式向它的词汇靠拢（任务状态、产物），将来加一个网关只是字段对照。

**opencode 走 ACP 还是走它自己的 HTTP 服务**：建议先 ACP。理由是同一份连接器代码之后能直接接 CodeBuddy（本机已装）和 Kimi，而 HTTP 那套只对 opencode 有效。但有三件事必须先验证（第 8 节的第零批），任何一件不成立就改走 HTTP 服务：

1. 在 `opencode acp` 下，sikeoop 现有的那个插件还会不会被加载（它负责写文件前的归属检查）。
2. opencode 要权限时，是不是通过 ACP 的权限请求发过来。
3. 发取消后它是不是很快停下。

## 4. 统一的任务格式

两个方向、所有接入方式都用同一份“任务单”和“回执”。它们是调度核心 `DispatchJob` 的对外写法，不是另一套模型。

### 4.1 任务单

```json
{
  "v": 1,
  "id": "任务编号（调度核心生成）",
  "parent": "上级任务编号（有的话）",
  "from": "sikeoop | Claude-1 | OpenCode-1 …",
  "to": "接手的 agent",
  "goal": "要做什么，写清目标。上限 4000 字，代码只给路径和行号",
  "context": {
    "roots": ["工作目录"],
    "owns": ["只允许它改的文件或文件夹"],
    "files": [{ "path": "src/a.ts", "lines": "40-90", "why": "要改的函数在这里" }],
    "handoff": ".sikeoop/handoff/<任务编号>.md",
    "refs": [{ "doc": "docs/xxx.md", "section": "3.2", "sha256": "…" }]
  },
  "accept": ["typecheck 通过", "test/foo.test.ts 通过"],
  "verify": { "typecheck": "npm run typecheck" },
  "limits": { "timeoutMs": 1800000, "network": false, "budgetLeft": 4 }
}
```

`scope`、`needs`、`verify`、`limits` 这些字段调度核心已经有，直接对应。新增的只有 `context.files`、`context.handoff`、`context.refs` 和 `accept`。

### 4.2 上下文交接：尽量不重读文件

沿用 `agent/handoff.ts` 的思路，做成一个**交接包文件**，放在项目里的 `.sikeoop/handoff/<任务编号>.md`，任务单里只写它的路径。接手的 agent 读这一个文件，代替重读一堆文件。

交接包里有：

- 目标和已经定下的决定。
- 试过什么、结果如何。
- 已经读过的文件片段：路径、行号范围、内容，以及读取时的内容哈希。接手方发现哈希对不上，就知道文件变了，要重读。
- 还没解决的问题。

规则和 `handoff.ts` 一致：读过的内容原样带上；超过大小上限时从最旧的开始省略，并注明“这段省略了，用到时重读”。

三条补充：

- **为什么用文件而不是直接塞进消息**：消息两头都要花 token（发的一方写一遍，收的一方读一遍），文件只读一遍。
- **续接同一个会话**：给同一个 agent 的后续任务，尽量发到它上一次的会话里（各家都有续接参数），它自己记得读过什么，连交接包都可以省。
- **不带密钥**：`.env`、密钥文件、被忽略的文件一律不进交接包。

### 4.3 进度

各家的事件统一成五种，节流后推给调度台，只保留最近若干条：

| 类型 | 含义 |
| --- | --- |
| `status` | 开始、在想、在等、结束 |
| `text` | 它说的话（增量） |
| `tool` | 它要用或用完了一个工具（名字、目标文件或命令的摘要） |
| `permission` | 它在请求权限，等审批卡 |
| `file` | sikeoop 自己看到某个文件变了 |

### 4.4 回执

```json
{
  "v": 1,
  "id": "任务编号",
  "status": "done | failed | cancelled | timeout | needs_input",
  "summary": "它的最后汇报（文字）",
  "files": { "changed": ["…"], "created": ["…"], "deleted": ["…"] },
  "claims": { "files": ["它自己说改了的文件"] },
  "checks": [{ "kind": "owns", "level": "pass", "summary": "改动都在它负责的文件里" }],
  "suggest": ["它建议接下来做的事"]
}
```

关键一点：**`files` 是 sikeoop 用前后快照量出来的，不是从 agent 的话里读出来的。** agent 自己声称的放在 `claims`，两者对不上会在 `checks` 里标出来。这套量法 `dispatch/verify.ts` 已经有，现在只是把结果也回传给派活的一方。

### 4.5 取消

取消一个任务会取消它派出去的所有子任务（已有）。到连接器这一层：先发协议里的取消；几秒内没停就结束进程。被取消的任务回执里仍然带上已经量到的改动清单，方便用户决定留不留。

## 5. 双向怎么走

### 5.1 出站：sikeoop → 外部 agent

1. 主对话、调度台、自动化、集群照旧向调度核心提交任务，执行体选 `agent`。
2. 调度核心做派活前检查，排队，轮到后交给连接器。
3. 连接器启动或复用对方的会话，把任务单的 `goal` 和交接包路径发过去。
4. 对方干活期间：进度推到调度台；它要权限就出审批卡；它写文件前（有前置钩子的工具）先过归属检查。
5. 结束后调度核心跑自动验收，生成回执。

### 5.2 入站：外部 agent → sikeoop 或别的 agent

在现有 MCP 服务上加四个工具（`list_peers`、`send_to` 保留）：

| 工具 | 作用 |
| --- | --- |
| `submit_task` | 提交一个任务：`to`（`sikeoop` 或某个 agent 的名字）、`goal`、可选的 `files` / `accept`。返回任务编号，不等结果 |
| `task_status` | 查一个任务的状态和最近进度 |
| `task_result` | 取回执。可以带一个等待时长，最多等这么久 |
| `cancel_task` | 取消自己提交的任务 |

规则：

- 提交的任务算作它**当前正在做的那个任务的子任务**，花同一棵树的预算。所以 A 派给 B、B 再派回 A 的来回，到预算用完就停，等用户。
- `to: "sikeoop"` 表示交给 sikeoop 自己的 agent（`session` 执行体）。
- 只能查和取消自己提交的任务。

### 5.3 不是 sikeoop 启动的 agent

用户在自己终端或 IDE 里开着的 agent 想参与，需要先**配对**：用户在 sikeoop 里点「允许外部 agent 接入」，sikeoop 生成一段带令牌的 MCP 配置，**由用户自己**贴到那个工具里（sikeoop 不改别人的配置）。配对可以随时撤销。这样进来的任务没有上级，单独成树，预算按“agent 发起”算（5 次），而且每个任务都要过审批卡。这一块放在最后一批。

## 6. 和调度核心怎么接

**新增一种执行体 `agent`，不复用 `cli` 或 `session`。**

| 执行体 | 是什么 | 就绪的判断 | 权限 | 进度 |
| --- | --- | --- | --- | --- |
| `cli` | 终端标签里的交互式会话 | 终端空闲 | 在终端里，或 Claude 的钩子 | 没有 |
| `session` | sikeoop 自己的 agent | 随时 | sikeoop 自己的审批 | 有 |
| `model` | 一次模型调用 | 随时 | 不涉及 | 流式文字 |
| `process` | 一个外部程序（Quarto） | 随时 | 不涉及 | 输出日志 |
| **`agent`（新）** | 通过结构化接口对话的外部 agent | 连接器说了算 | 对方发请求，sikeoop 出卡 | 结构化事件 |

不复用的理由：硬塞进 `cli` 会让“终端空闲才能派”这个判断到处加例外；塞进 `process` 又丢了权限和会话。新增一种的代价很小——上次加 `process` 只动了类型里一行和调度台一个标签。

实现上是一个 `AgentExecutor` 类加一个**连接器**接口，连接器有三种实现：`acp`、`http`（opencode 专用，备选）、`headless`（一次性调用）。执行体种类只有一个，不按协议分。

对现有类型的改动（都是新增）：

- `DispatchExecutorKind` 加 `"agent"`。
- `DispatchJob` 加可选的 `context`（4.1 里新增的那几个字段）和 `progress`（最近几条进度）。
- `DispatchJob.result` 加可选的 `files`。
- `DispatchEvent` 加一种进度事件。

CLI 扩展的 JSON 定义加一个可选的 `connect` 段（比如 `{ "type": "acp", "args": ["acp"] }`），这样用户接一个支持 ACP 的新工具仍然只写 JSON，不用改 sikeoop 的代码。没有 `connect` 的定义照旧走终端。

## 7. 安全

| 风险 | 做法 |
| --- | --- |
| **外部 agent 擅自干活** | 启动外部 agent 要过审批卡（已有）。它运行中的每个权限请求都转成审批卡，超时按拒绝处理。**永远不传** `--auto`、`--yolo`、`--force`、`--dangerously-*` 这类全放开的参数。一次性调用没法来回问权限，只能用于事先限定为只读或限定了可写范围的任务。 |
| **写到目录外或别人的文件** | 任务的工作目录就是它的启动目录。有前置钩子的工具（Claude Code、opencode、走中立协议的扩展）在写之前拦。没有前置钩子的（Codex、Aider、Cursor CLI）用它自己的沙盒（Codex 的 `-s workspace-write`），加事后的越界检查标红，由用户决定是否回滚——这是调度核心方案 D2 已定的做法。可选：给这类工具开独立的 git worktree。 |
| **互派停不下来** | 任务树预算（已有：agent 发起 5 次）。再加三条：派活深度上限 3 层；不能派给自己；同一对 agent 每分钟的提交次数有上限。预算用完产生事件，等用户。 |
| **外部 agent 的输出里夹带指令** | 外部 agent 的输出一律当数据。四条硬规则：① sikeoop 不从 agent 的文字里解析命令去执行；② 回执里的结构化字段（状态、文件清单）由 sikeoop 自己生成，不从文字里读；③ agent 的“建议下一步”只展示，不自动变成任务——要派活只有 `submit_task` 一条路，而它受预算和审批约束；④ 转交给另一个 agent 时带上来源标记（现有的「[X → 你]」），并去掉终端控制字符、限制长度。即使接手的模型被文字带偏，它能做的每一步仍然要过上面的审批和归属检查。 |
| **凭据跨工具泄露** | 每个工具用它自己的登录，sikeoop 保存的服务商密钥不传给任何外部工具。传给子进程的环境变量走白名单（现有的 `envPassthrough`）。MCP 令牌每个会话一个，只在本机有效，会话结束即作废。交接包和日志不含密钥文件。 |
| **本机端口被别的程序利用** | ACP 走标准输入输出，不开端口。如果用 opencode 的 HTTP 服务：只绑 `127.0.0.1`，每次启动通过环境变量设一个随机密码，绝不开 `--mdns`。 |
| **改了别人的配置** | 一律通过命令行参数和环境变量给单次会话加设置，不写任何工具的全局配置（现有做法）。配对时的配置由用户自己贴。 |
| **入站任务来路不明** | 没配对的进不来。配对进来的每个任务都要审批；文件信箱（如果做）里的任务同样当作不可信，逐个审批。 |

有一件事要说明：调度核心方案里的“统一审批路由”按用户 10 月 10 日的决定暂缓了。本方案的审批卡先接在现有的灵动岛通道上；如果之后恢复那项工作，这里跟着切过去。

## 11. 第零批实验结果（2026-10-11，实测）

指挥官授权实际启动了一次 `opencode acp`，在临时空目录里的一个小测试项目上做最小任务，确认第 3 节的三个前提。没有改 opencode 的全局配置，没有全局装插件（插件和模型都通过 `OPENCODE_CONFIG_CONTENT` 只对这一次进程生效，和 sikeoop 现在启动 opencode 的办法一样）。

### 怎么做的

- 本机 opencode 1.18.30。写了一个约 140 行的最小 ACP 客户端（JSON-RPC over stdio），启动 `opencode acp` 子进程。
- 用一个便宜模型（zhipu/glm-4-flash，凭用户全局配置里已有的 provider）跑三个小任务：读一个文件、往一个文件追加一行、数到 100 然后中途取消。一共约 4 次模型调用，在授权的 5 次以内。
- 客户端里起了一个本机 HTTP 小服务，接 sikeoop 那个 opencode 插件的上报，用来看插件在 ACP 模式下会不会加载。

### 三个问题的答案：都成立

**1. ACP 模式下 sikeoop 的插件会不会加载？会。** 通过 `OPENCODE_CONFIG_CONTENT` 传进去的插件在 `opencode acp` 下正常加载，`event` 和 `tool.execute.before` 两个钩子都触发了，收到了 `turn-start` / `tool` / `waiting` / `turn-end`，一共 11 条上报。写文件前插件先拒绝一次（测试用）也生效了——模型收到拒绝后改成向用户确认，没有硬写。

**2. 权限请求走不走协议？走。** 配了 `permission: { edit: "ask", bash: "ask" }` 后，opencode 在要用工具时通过 ACP 发来 `session/request_permission`，带结构化的 `toolCall`（`toolCallId`、`kind`、`locations`、`rawInput`）和一个选项列表 `[{optionId:"once", kind:"allow…"}, …]`。客户端回 `{outcome:{outcome:"selected", optionId:"once"}}` 被接受。**正好能接到 sikeoop 的审批卡：卡上列选项，用户点哪个就回哪个 optionId。**

**3. 取消及不及时？及时。** 发一条 `session/cancel` 通知后，正在跑的 `session/prompt` 几乎立刻（约 20 毫秒内）返回 `stopReason: "cancelled"`，干净利落。

### 顺带摸清的协议细节（对第一批有用）

- `initialize` 返回能力清单：`loadSession`、会话的 `fork`/`list`/`resume`/`close`、MCP 的 http+sse、`embeddedContext`、`image`；还有 `authMethods`（没登录时提示 `opencode auth login`）。
- `session/new` 返回 `sessionId`，并带 `configOptions`：可选模型的完整列表，以及一个 `mode`（`build` / `plan`，**`plan` 模式禁用所有编辑工具**——正好用来跑“只读”任务，对应第 9 节第 7 条）。
- 进度统一从 `session/update` 通知来，子类型有：`agent_message_chunk`（流式文字）、`tool_call`、`tool_call_update`（状态 `pending` / `in_progress` / `failed` / `completed`）。一轮结束由 `session/prompt` 的响应带 `stopReason` 给出。

### 由此修正第一批的两点设计

1. **ACP 模式下那个 opencode 插件基本可以不要。** 它当初是为“往终端打字”补的（终端没有结构化通道）。ACP 自己就给了轮次边界（prompt 的请求/响应）、流式文字、工具调用、权限请求，连接器直接从协议读即可。插件和 ACP 的权限请求同时开着会**重复**——实验里两条权限通道都触发了。第一批应只走协议这一条，插件最多保留用于协议没覆盖的事件，不参与权限。
2. **权限选项要原样透传。** `session/request_permission` 的 `options` 由 opencode 给（“仅此一次 / 一直允许 / 拒绝”等），审批卡应把这些选项照原样显示，用户选了回对应的 `optionId`，不要在中间自己翻译成允许/拒绝，免得丢掉“一直允许”这类选项。

### 没验证的

- 只测了 opencode，没测 CodeBuddy（本机也装了，留到第四批验证连接器是否通用）。
- 读文件那次工具最后 `failed`，是便宜模型 glm-4-flash 把路径写成了 `/hello.txt`（根目录）而不是相对路径，属于模型犯错，不是协议或权限的问题；换强一点的模型应该不会。
- 没有测会话续接（`session/resume`）、`loadSession`、多会话并发，这些留到第三批。
- 结论基于 opencode 1.18.30 这一个版本。

**结论：第一批按 ACP 走。** 实现任务书见 `docs/打洞-第一批任务书.md`。
