## 3. 第一批：调度器正确性

### F1 排队超时从提交时算起

**现象** 回归面板默认一批 50 条、每条最多 5 分钟（`src/main/regress/view.ts:6`），全部排在同一个会话上（`src/main/regress/service.ts:154`），只能一条条跑。约 60 分钟后，后面还在正常排队的条目全部以「排了 60 分钟的队」失败。跨项目 session（`session/service.ts:362`）、群聊（`group/service.ts:151`）和 PV 工坊（`pv/service.ts:59`）都用 lane 串行，同样会中招。叠加 F11，主对话的派活也可能因为全局名额被长任务占满而超时失败。

**根因** `scheduler.ts:279-283` 用 `Date.now() - job.createdAt` 计时。这个超时本来是防「执行体一直不空」（比如会话卡在等用户），但现在把调度器自己造成的等待（同一执行体积压、lane 积压、名额满）也算进去了。

**修改方案**

1. `Entry` 增加 `stuckSince?: number`，表示「执行体自己不可用」从什么时候开始。
2. `pump()` 里每个排队任务按下面的顺序判断阻塞原因，**在名额检查之前**完成：

   | 顺序 | 条件 | 原因 | 计时 |
   |---|---|---|---|
   | 1 | `!executor.alive()` | 已退出 | 直接以 `exited` 结束（不变） |
   | 2 | `current(ref)` 存在，或 `laneBusy(lane)`，或冲突（F5） | 调度器自己的积压 | `stuckSince = undefined` |
   | 3 | `!executor.ready()` | 执行体不可用 | `stuckSince ??= now` |
   | 4 | 名额满（F2 规则判定后仍不能放行） | 名额 | `stuckSince = undefined` |
   | — | 都不满足 | 可以启动 | — |

3. 超时判断改成 `stuckSince !== undefined && now - stuckSince >= queueTimeoutMs`。错误文案改成：`排了 N 分钟的队，${name} 一直没空出来，任务没有派出去`。开头保留「排了 N 分钟的队」，因为已有用例用正则 `/排了 .* 分钟的队/` 断言这段文字（`test/dispatch/scheduler.test.ts:374`）。
4. 把阻塞原因写到 `job.waiting`（第 7 节），调度台据此显示「在等 Claude-1 空出来」「在排 lane」「名额已满」。只在原因变化时调用 `changed()`，避免每 2 秒发一次事件。
5. 不加绝对上限。用户可以随时取消；需要上限时由调用方传 `timeoutMs`。

**接口变化** `DispatchJob.waiting?`（第 7 节）。`DispatcherOptions.queueTimeoutMs` 含义改为「执行体连续不可用的时长」，默认值不变（1 小时）。

**测试**

- T1-1：同一执行体 5 个任务，`queueTimeoutMs=100`，每个跑 40ms → 全部 `done`（复现 A）。
- T1-2：同一 lane、不同执行体，同样的时序 → 全部 `done`。
- T1-3：已有用例「a job that waits too long in the queue is given up as timed out」（执行体 `busy=true`）不改，必须继续通过。
- T1-4：执行体先不可用 50ms，再可用但被调度器的另一个任务占着 100ms，`queueTimeoutMs=80` → 不超时（计时被清零）。

**验收** `node --test test/dispatch/` 全过，含 T1-1 至 T1-4。

**风险** 一个 lane 的队首如果一直在跑，后面的任务会无限期排队。这个等待受队首任务自己的 `timeoutMs` 约束，可以接受。

### F2 子任务绕过并发上限

**现象** `scheduler.ts:285-286`：只要父任务在跑，子任务就完全不受上限约束，实际只受预算限制（自动化 30，其他 20）。真实路径是自动化的 agent 步骤：它本身就是一个运行中的任务，又能通过 `send_to_agent` 的 `tasks` 一次派出多个任务。复现 B：上限 4 时实际跑到 13 个。

反过来，父任务一进入 `waiting_approval`（`scheduler.ts:180`），就不再算「在跑」，它的子任务失去豁免（复现 C）。目前只有 opencode 任务会进入这个状态，而它不会派子任务，所以这是潜在问题，但规则要一起修正。

**根因** 豁免的本意是防止「父任务占着名额等子任务、子任务等名额」的死锁，但豁免没有数量限制。

**修改方案**

1. 定义「活跃」状态：`ACTIVE = new Set(["starting", "running", "waiting_approval"])`。
2. `Entry` 增加 `overCap?: boolean`；`DispatchJob` 增加同名可选字段，供调度台显示。
3. 名额判断改成：

   ```ts
   // 名额满时，只有父任务活跃、且没有兄弟任务正在超额运行的子任务可以放行（每个活跃父任务至多一个超额子任务）
   const parent = e.job.parentId ? this.entries.get(e.job.parentId) : undefined;
   const mayOverflow = !!parent && ACTIVE.has(parent.job.status) && !this.siblingOverCap(e.job.parentId!);
   if (running >= this.maxRunning && !mayOverflow) { /* 原因：名额 */ continue; }
   e.overCap = e.job.overCap = running >= this.maxRunning;
   ```

   `siblingOverCap(parentId)` 检查：存在 `parentId` 相同、不在排队、且 `overCap` 为真的条目。
4. F11 落地后，这条规则按池分别生效。

**为什么不会死锁** 每个活跃父任务总能让一个子任务先跑起来；那个子任务如果又派了孙任务，孙任务的父任务（这个子任务）也是活跃的，同样能放行一个。所以任何一条「父等子」链都能推进。总并发上限是「名额＋正在等子任务的父任务数」，实际受预算和树深约束，远小于现在。

**测试**

- T2-1：上限 4，运行中父任务挂 12 个子任务 → `view().running === 5`（复现 B 改断言）。
- T2-2：已有用例「a running job's children skip the cap…」（上限 1）继续通过。
- T2-3：上限 1，三层链：根 → 子 → 孙，每层都等下一层 → 三个都能启动并依次完成。
- T2-4：上限 1，父任务收到 `permission` 进度后派子任务 → 子任务启动（复现 C 改断言）。
- T2-5：同一父任务两个子任务，名额满 → 只有一个超额运行，它结束后第二个才启动。

**验收** `node --test test/dispatch/` 全过，含 T2-1 至 T2-5。

**风险** 批量派活在名额满时会变成「超额一个、其余排队」，比现在慢。这是预期行为，也是上限的本意。

### F3 进度事件导致日志写放大

**现象** `scheduler.ts:183` 在每次 `progress()` 时都调用 `changed()`，发出完整的 `job` 事件。`index.ts:407-412` 收到后会做三件事：写日志（`store.ts:33-38` 只跳过 `queued`，每行都带最多 100 条进度）、`crossSessions.sync()`、`regress.jobChanged()`。模型子代理每次工具调用都会触发一次（`index.ts:1160`），opencode 每条进度也会。复现 D：一个任务 300 次进度产生约 2.16MB 日志。`store.ts` 头注释写的是「开始和结束时各记一次」，实际行为和注释不符。

**修改方案**

1. `scheduler.ts` 的 `progress()`：照旧追加进度、发 `progress` 事件；**只有状态真的变了**（`running` ↔ `waiting_approval`）才调用 `changed()`。渲染层已经在 `DispatchConsole.tsx:146-147` 自己把 `progress` 事件追加到任务上，节流快照（`dispatchChangedSoon`）也照旧会发，所以不需要 `job` 事件。
2. `store.ts` 的 `JobLog.record()`：
   - 记住每个任务上次写入的状态（`Map<id, status>`）。未结束的任务状态没变就不写；已结束的任务每次都写（`markNeedsReview`、F8 的迟到结果需要追加）。
   - 写入时裁剪：未结束的行去掉 `progress`；结束行只保留最后 20 条进度，并去掉其中的 `permission` 卡片。
   - 修正头注释。
3. `index.ts:407-412` 不用改：`job` 事件变少以后，`sync()` 和 `jobChanged()` 自然只在状态变化时触发。

**测试**

- T3-1（scheduler）：300 次 `tool` 进度 → 状态变化之外没有 `job` 事件；`progress` 事件 300 次。
- T3-2（store）：同一任务依次记录 running、running、running、done → 文件 2 行；结束行 `progress.length ≤ 20`。
- T3-3（store）：已结束任务再记录一次（模拟 `markNeedsReview`）→ 追加 1 行，`load()` 取到最新一行。

**验收** T3-1 至 T3-3 通过；复现 D 的 job 事件数 ≤ 2。

**风险** 历史任务只保留最后 20 条进度。调度台展开历史任务时看到的进度会变短，可以接受。

### F4 模型子代理的结果无人回收

**现象** `send_to_agent` 派给模型子代理时，默认只等 20 分钟（`tools/agent-bus-tools.ts:53`），而子代理任务的超时是 31 分钟（`index.ts:1116`）。等待到期后，`waitJob` 返回「可以之后用 wait_agent 继续等」（`agent-bus-tools.ts:91`），但 `wait_agent` 是用 `deps.find`（也就是 `peers.hostFind`）找名字的（`:303`），找不到「供应商/模型」这种名字，只会报错。子代理会继续跑完，结果却只出现在调度台，指挥官拿不到。

**修改方案**

1. 新增公开方法 `Dispatcher.wait(jobId): Promise<DispatchJob> | undefined`：任务还在跑就返回结束时的 Promise（复用现有私有的 `whenDone`）；任务在历史里就返回已完成的 Promise；不认识的 id 返回 `undefined`。
2. `AgentBusDeps` 增加 `job(id: string): Promise<DispatchJob> | null`，由 `index.ts` 用 `dispatcher.wait` 实现。
3. `send_to_agent` 派给子代理时：
   - 默认等待时间改为 `WORKER_WAIT_MIN = 32`，比子代理超时长，默认情况下一定能等到结果；
   - 调用方显式给了更短的 `wait_minutes`、到期还没完时，返回文案带上任务编号：`… 还没做完（任务 #<id 前 8 位>）。之后用 wait_agent（job="<完整 id>"）取结果。`
4. `wait_agent` 增加可选参数 `job: string | string[]`，按任务 id 等待，结果格式和按会话名等待一致；`to` 和 `job` 至少要给一个。`to` 里出现「/」（模型名）时，给出明确提示：「子代理请用 job 参数等」。
5. `waitJob` 的超时文案按目标区分：终端会话提示用 `to`，子代理提示用 `job`。

**接口变化** `AgentBusDeps.job`；`wait_agent` 的输入 schema 增加 `job`（工具 schema 在 `agent-bus-tools.ts` 内，不涉及 `shared/types.ts`）。`Dispatcher.wait` 是 `dispatch/` 内部接口。

**测试**（`test/tools/agent-bus.test.ts`）

- T4-1：子代理任务不传 `wait_minutes`，假 `done` 在 25 分钟（用假计时）后完成 → 返回结果，不是「还没做完」。
- T4-2：`wait_minutes=1`、子代理未完成 → 文案含任务 id；随后 `wait_agent({ job })` 拿到结果。
- T4-3：`wait_agent({ to: "openai/gpt-x" })` → 文案提示改用 `job`。

**验收** T4-1 至 T4-3 通过；已有 agent-bus 用例全过。

### F14 重启后排队中的任务无痕消失

**现象** `store.ts:38` 不记录 `queued` 状态，应用退出时还在排队的任务在历史里完全看不到。`load()` 把未结束的任务一律标成「应用关闭时它还没做完」（`store.ts:75`），没有区分「在跑」和「在排队」。

**修改方案**（和 F3 一起改 `store.ts`）

1. `record()` 对 `queued` 也写一行（受 F3 的「状态没变不写」约束，每个任务只写一次）。
2. `load()` 区分两种情况：从未开始的写「应用关闭时还在排队，没有派出去」；开始过的维持原文案。两种都标成 `exited`。

**测试** T14-1：记录 queued 后直接 `load()` → 状态 `exited`，错误文案是「还在排队」。
**验收** T14-1 通过。

## 4. 第二批：并行写入的冲突控制

### F5 准入按文件归属排他

**现象** 调度器准入时不看 `scope.owns`。两个写入范围重叠的任务，或者不写 `owns`（也就是可写整个项目）的任务，会在同一目录里被同时放行。冲突要么在写文件时才被锁拒绝（只对 Claude Code 和 sikeoop 自己的工具有效，见 F6），要么只能事后由验收发现（Codex、扩展 CLI）。LEGION 第五章要求「每个文件只有一个负责人」，调度器目前没有在准入环节执行这条规则。

**修改方案**

1. `scope` 增加 `readOnly?: boolean`（第 7 节）。会设置它的调用方：
   - 集群只读角色：`runHarmonyRole` 按 `role.readOnly` 设置（`index.ts:1015`）；
   - opencode 只读模式（`dispatch/agent-service.ts:46`）。
2. `guard.ts` 新增两个纯函数：
   - `writeSet(job)`：没有 `scope` 或 `readOnly` 时返回 `null`；没有 `owns` 时返回 `"all"`；否则返回每个 `owns` 模式的**字面前缀**（第一个 `*` 之前、截到最后一个 `/` 为止）解析成的绝对路径。
   - `mayOverlap(a, b)`：任一方是 `null` → 不冲突；两者的 `roots` 互不包含 → 不冲突；任一方是 `"all"` → 冲突；否则只要有一对前缀互相包含（复用 `isInside`，大小写规则同 `FOLD_CASE`）就算冲突。

   这个判断是**保守**的：只可能多串行，不会漏判。
3. `pump()` 在 F1 表格的第 2 步加入冲突判断：存在一个**非排队**的任务 `o` 满足 `mayOverlap(e.job, o.job)`，并且 `o` 既不是 `e` 的祖先也不是 `e` 的后代，就记为「调度器自己的积压」，`job.waiting = { reason: "conflict", detail: o.job.executor.name }`。

   **祖先和后代必须豁免**，否则「父任务写整个项目、等子任务」会直接死锁。
4. `DispatcherOptions.conflict?: "strict" | "declared" | "off"`，默认值由 D3 决定：
   - `strict`：不写 `owns` 视为可写整个目录，和同目录的所有写入任务互斥；
   - `declared`：只在**双方都写了 `owns`** 且重叠时互斥，不写的照旧并行；
   - `off`：回退开关，不做冲突判断。
5. 工具文案：`send_to_agent` 和 `dispatch_agent` 的 `owns` 说明补一句「并行派活必须写 owns，范围重叠或不写的会排队」。任务因冲突排过队的，结果里附一行说明。

**接口变化** `scope.readOnly?`、`DispatchJob.waiting?`（第 7 节）；`DispatcherOptions.conflict`。

**测试**

- T5-1（guard）：`mayOverlap` 真值表：`["src/a/"]` 对 `["src/a/x.ts"]` → 冲突；对 `["src/b/**"]` → 不冲突；`"all"` 对任意 → 冲突；只读 → 不冲突；不同 roots → 不冲突；`["src/**/x.ts"]` 的前缀是 `src/` → 对 `["src/b/"]` 冲突（保守）。
- T5-2（scheduler）：两个 `owns` 重叠的任务派给不同执行体 → 第二个等第一个结束；不重叠 → 并行。
- T5-3：父任务 `scope` 是整个目录，子任务写同一目录 → 子任务照常启动（祖先豁免）。
- T5-4：`strict` 下两个不写 `owns` 的任务 → 串行；`declared` 下 → 并行。
- T5-5：因冲突排队的时间不计入 F1 的排队超时。

**验收** T5-1 至 T5-5 通过；已有 dispatch 和 agent-bus 用例全过。

**风险** `strict` 会让「不写 owns 的批量派活」从并行变成串行，属于行为变化，见 D3。

### F6 文件锁覆盖不全，长任务的锁中途过期

**现象**

1. 只有两个地方会加锁：Claude Code 的 PreToolUse 钩子（`peers.ts:470`）和 sikeoop 自己的编辑工具（`tools/edit-tools.ts:42`）。
2. opencode 的权限回调只检查文件归属，不加锁（`dispatch/agent.ts:31-36`）。
3. Codex、扩展 CLI 和所有 shell 命令都没有写前拦截，无法加锁。
4. 锁的 TTL 是 10 分钟（`session/locks.ts:3`），而任务超时是 30 分钟。一轮早期写过的文件，锁会在这一轮结束前悄悄过期。

**修改方案**

1. **续期**：`FileLocks` 增加 `touch(owner)`，把这个 owner 的所有锁顺延到「现在＋TTL」。调用点：
   - PeerBus 收到该会话的任何钩子或 RPC 事件时（`peers.ts` 的 `hook()` 和 `rpc()` 入口）；
   - PeerBus 收到该会话终端输出时（`output()`），每个 owner 每 30 秒至多一次，避免对每块输出遍历整张锁表；
   - sikeoop 自己的会话每次开始工具调用时（`agent/loop.ts`，owner 是 `app:${id}`）。

   TTL 保持 10 分钟，只用来兜底进程崩溃后的残留锁。
2. **opencode 加锁**：`AgentExecutor` 的权限回调在归属检查通过后，调用 `fileLocks.acquire(this.ref, 路径列表)`；拿不到锁就拒绝（返回 `null`），并发一条进度说明是谁占着。在 `run()` 的 `finally` 里 `fileLocks.release(this.ref)`。
3. **拿不到锁的 Codex、扩展 CLI 和 shell 命令**：明确列为已知限制，靠 F5 的准入排他和事后验收兜底。不再尝试拦截。

**测试**

- T6-1（locks）：`acquire` 后过 TTL−1ms 再 `touch`，再过 TTL−1ms → 锁仍在；不 `touch` → 过期。
- T6-2（agent executor）：另一个 owner 持锁时，opencode 的写权限请求返回 `null`；`run()` 结束后锁被释放。

**验收** T6-1、T6-2 通过。

### F7 类型检查验收的并发归因与返工

**现象**

1. `verify.ts:173-183` 直接拿开始前的基线和结束后的结果对比，新增错误全部算在当前任务头上。文件归属检查（`:149-169`）会把同时在跑的其他任务排除在外，类型检查却没有。
2. `scheduler.ts:383-386` 遇到类型检查 `fail` 就自动返工。结果是兄弟任务引入的错误，会被派给这个终端去修。
3. 并发任务各自跑一遍同样的 tsc，CPU 争用严重。

**修改方案**

1. `typeErrors()` 旁边新增 `typeErrorList(output): { key: string; file: string }[]`，`file` 按 `roots[0]` 解析成绝对路径。`typeErrors()` 保留，内部改为调用新函数。
2. `Verifier.after()`：
   - 「同时在写的任务」= `meanwhile` 里 roots 有交集、且 `scope.readOnly` 不为真的任务；
   - 把新增错误分成两类：**本任务的**（错误所在文件在本任务的改动列表里）和**其他的**；
   - 没有同时在写的任务：维持现状，全部新增错误都是 `fail`；
   - 有同时在写的任务：只有「本任务的」新增错误判 `fail`，details 只列这些；「其他的」单独写一条 `warn`：「另有 N 个新增错误不在它改过的文件里，可能来自同时在干活的 X」。
3. 返工（`scheduler.ts` 的 `rework()`）只看 `fail` 级的类型检查结果，所以不需要改：它自然只会带上「本任务的」错误。
4. **同一检查共享一次运行**：`Verifier` 增加 `inflight: Map<string, Promise<Set<string> | null>>`，键是「cwd＋命令＋快照签名」，签名相同的并发请求共用一个 Promise。再加一把按「cwd＋命令」区分的串行锁，同一项目同一时间只跑一个 tsc。

**测试**（`test/dispatch/verify.test.ts`）

- T7-1：没有并发任务，新增错误在别的文件 → 照旧 `fail`。
- T7-2：有并发写入任务，新增错误不在本任务改动的文件里 → 只有 `warn`，没有 `fail`。
- T7-3：有并发写入任务，新增错误在本任务改动的文件里 → `fail`，details 只含这些。
- T7-4：两个任务同时调用 `before()`，快照相同 → 命令只执行一次。

**验收** T7-1 至 T7-4 通过；`test/dispatch/scheduler.test.ts` 里和返工有关的用例全过。

**风险** 改了 A 文件的导出类型、错误却出现在调用方 B 文件，这种情况在并发时会被降级成 `warn`。这是有意的取舍：宁可少返工一次，也不能让任务去修别人的错误；`warn` 照样会出现在交给指挥官的结果里。

### F8 终端任务超时后的迟到结果

**现象** 终端任务超时后，会话会被留着继续跑（`dispatch/cli.ts:65-69`，这是有意的设计），但迟到的结果被丢弃了。之后调用 `wait_agent` 时，`last()` 要求 `job.endedAt >= s.since`（`index.ts:1090-1093`）；会话后来变成空闲时 `since` 会更新，这个条件就不成立了。最后只能回一句「空闲」，加上截断到 60 字的 `detail`。

**修改方案**

1. `CliExecutor` 构造参数增加可选的 `late?: (jobId: string, text: string) => void`。`turn()` 发现中止原因是 `"timeout"` 时，在后台再挂一个 `bus.waitTurn(ref, LATE_MS = 2 * 60 * 60_000, 一个不会被中止的 signal)`；拿到文本就调用 `late(job.id, text)`。这个监听一定拿到的是本任务那一轮：会话忙着的时候调度器不会投下一个任务。
2. `Dispatcher` 增加 `late(jobId, result)`：只对状态为 `timeout` 的历史任务生效，写入 `result`，并设置 `job.lateAt = now`。状态保持 `timeout`，不改变状态语义。然后发出 `job` 事件（已结束的任务按 F3 规则会追加日志）。
3. `index.ts` 的 `last()` 条件改为 `(job.lateAt ?? job.endedAt ?? 0) >= s.since`。
4. 由 PeerBus 互发产生的任务（`index.ts:528-535`），在 `late` 回调里**不再**补发回复任务：提问方已经收到「超时了」的回复，再补一条容易让双方来回对话。迟到结果只在调度台和 `wait_agent` 里可见。

**测试** T8-1：超时 → 稍后假 Stop 带文本 → `dispatcher.jobs()` 里该任务 `lateAt` 有值、`result.text` 正确、状态仍是 `timeout`。T8-2：没超时的任务不挂后台监听。
**验收** T8-1、T8-2 通过。

### F10 卡死检测与供应商感知

**现象** CLI 进程挂起时（进程还在，没有任何输出或钩子），会话会一直显示 `working`。结果是队列里的任务要等满 60 分钟，正在跑的任务要等满 30 分钟（进程退出则会通过 `startProgram` 的回调注销，这种情况没问题）。另外，供应商健康状态只用在 `list_agents` 的展示上（`index.ts:1095-1100`），派活时不会避开被限流的供应商；每个子代理任务的 ref 都不一样（`index.ts:1115`），所以同一个模型的并发也不受限制。

**修改方案**

1. `Session` 增加 `lastSignalAt`，以下事件都会更新它：钩子事件、RPC 请求、终端输出（`output()` 对所有会话生效，不再只对靠「安静」判断回合的会话生效）。
2. PeerBus 加一个 30 秒的看门狗：状态是 `working` 或 `waiting`、并且 `now - lastSignalAt > STALL_MS`（默认 15 分钟）→ 设置 `stalled = true`，调用一次 `onNotice("waiting", …, "疑似卡住：15 分钟没有任何输出")`。收到任何信号就清除。**不自动结束进程。**
3. `AgentSessionView` 增加 `stalled?: boolean`（第 7 节）。调度器把 `stalled` 视为执行体不可用，F1 的计时照常运行；正在跑的任务追加一条进度 `{ type: "status", text: "stalled" }`。
4. 供应商限流放到 F11 的并发键里统一处理（`provider:<id>`），这里不单独实现。

**测试** T10-1：用假时钟让会话 15 分钟没有信号 → `stalled` 为真、通知只发一次；之后来一次输出 → 清除。

## 6. 第四批：控制面与收尾

### F12 调度台控制：重试、追加预算、暂停

**现象** IPC 只有查看、取消，以及 opencode 的提交和审批（`preload/index.ts:261-273`）。预算耗尽时，灵动岛提示「等你确认再继续」（`index.ts:415-418`），但没有任何地方可以确认；被拒的派活请求也直接丢掉了（`scheduler.ts:143-145`）。

**修改方案（后端）**

1. `Dispatcher.grant(rootId, n)`：给还在列表里的树追加预算（`left += n`、`total += n`），发出 `{ type: "budget", budget }` 事件。树已经结束时报错「这串任务已经结束」。只有调度台能调用，**不在灵动岛上加按钮**，避免出现第三条审批通道（见 D5）。灵动岛提示文案改为「去调度台点『继续』」。
2. `Dispatcher.retry(jobId)`：依赖新选项 `recreate?(job): Executor | null`，由 `index.ts` 实现：
   - `cli`：会话还在（`peers.viewOf(ref)`）就返回 `cliExecutor(view)`；
   - 模型子代理：从 ref `worker:<name>#n` 解析出模型名，用同一个工厂新建执行体；
   - 其他类型（集群角色的输入信封没有保存、闭包型执行体）返回 `null`，表示不支持重试。

   重试会提交一个**新树**：`origin: "user"`、`from: "调度台"`、`retryOf: 原 id`，`input`、`scope`、`needs`、`verify` 和超时都沿用原任务。
3. `view()` 给已结束的任务计算 `retryable`，前端据此决定是否显示「重试」。
4. `Dispatcher.pause(paused)`：暂停时 `pump()` 不再启动新任务，已在跑的不受影响；`view.paused` 反映状态。暂停期间的等待不计入 F1 的排队超时。
5. 新增 IPC 通道，参数都要校验：
   - `dispatch:grant(rootId: string, n: 1–20 的整数)`；
   - `dispatch:retry(jobId: string)`；
   - `dispatch:pause(paused: boolean)`。

**修改方案（前端，Claude 军团）** 在 `DispatchConsole.tsx` 里：

- 任务树的预算用完时，树头显示「再给 5 次」；
- 可重试的已结束任务显示「重试」；
- 顶部加「暂停派活/继续派活」开关；
- `dev-mock.ts` 补上对应的假实现。

### F13 手机端的调度视图

**现象** README 写的是「用手机派活、看进度、点批准」，但手机端的 `agents.list` 里，`pending` 被固定成空数组（`index.ts:1600`）。PeerBus 的待批请求其实存在，手机也能通过 `agents.respond` 应答，却永远看不到有什么要批。调度队列在手机上完全不可见，也不能取消任务。

**修改方案**

1. PeerBus 增加 `pendingAsks(): { id; sessionName; title; detail; createdAt }[]`，`agents.list` 用它填 `pending`。这一项是现有功能的缺陷，单独修，不依赖协议变更。
2. `MobileRpcDispatcher` 新增两个方法，只对已批准的设备开放：
   - `dispatch.list`：活跃任务加最近 20 条已结束任务，只返回精简字段（`id`、`rootId`、`parentId`、执行体名、状态、`from`、`input` 前 200 字、时间、错误），不带进度；
   - `dispatch.cancel { jobId }`。
3. `protocol/` 的方法清单同步更新，版本号加一；Android 和 iOS 的界面另立任务。

**测试** 放在仓库根目录的 `test/mobile/gateway.test.mjs`，沿用其中现有的 `agents.list` 用例写法（约第 246 行）。T13-1：未批准的设备调用 `dispatch.list` 被拒；批准后返回精简字段且不含 `progress`。T13-2：有一个 PeerBus 待批请求时，`agents.list` 的 `pending` 长度为 1。
**验收** T13-1、T13-2 通过。
