# 鲸渲：技术定位与开发方向

> **已被取代（2026-10-10）**：总方案见 `sikeoop-game-kit.md`。鲸渲以后作为可选特效库，本文的技术原则和 M4 平台约定仍可参考。


> **注意：范围已扩大为「引擎 + 网页可视化编辑器」，总方案见 `jingxuan-engine.md`，冲突之处以它为准（尤其本文第 5 节「不做可视化编辑器」已作废）。**
>
> 2026-10-10，第 3 版（新增：开发初期只针对 macOS M4 以上芯片；第 8.5 节「生态互通」）。架构细节见同目录的 `webgpu-engine.md`（下称「设计稿」）。
> 名字：中文「鲸渲」，英文和代码标识 `jingxuan`，npm 包名 `@sikeoop/jingxuan`。

## 1. 一句话定位

**鲸渲是给 AI 用的 WebGPU 游戏渲染引擎。**
- 核心能力是 GPU 粒子和 shader 特效。
- 每一帧都能被 AI 看懂、复现、验证。
- 它是 sikeoop「智能体做网页游戏」这条路线的渲染底座。

## 2. 为什么要自己做

市面上已经有成熟的网页渲染引擎：Three.js、Babylon.js、PlayCanvas 偏 3D，PixiJS、Phaser 偏 2D。其中好几家已经支持 WebGPU。鲸渲不在「功能多」上和它们比，而是盯住它们都没解决的三件事：

| 现有引擎的情况 | 鲸渲的做法 |
|---|---|
| 首先面向人类开发者。AI 改完代码，只能靠人看画面判断对不对 | **每一帧可读**：`inspect()` 把各 pass 耗时、绘制调用数、粒子数量、显存、shader 报错导出成 JSON，sikeoop 内置浏览器里的 AI 直接就能读 |
| 渲染结果每次都有细微差别，没法用截图做测试 | **确定性渲染**：固定步长、随机数由种子决定、操作能回放。同样的输入，每次得到同一张图，截图本身就是测试 |
| 背着 WebGL 兼容的历史包袱。粒子大多还在 CPU 上算，或者只能作为额外插件 | **只做 WebGPU**：从第一行代码起就按计算着色器、间接绘制、存储缓冲来设计。百万级粒子是默认能力，不是附加功能 |
| shader 报错只给拼装后的代码行号，人都看不懂，AI 更难修 | **报错能直接看懂**：指出出错的源文件和行号，附中文说明，AI 读到报错就能直接修 |

**结论**：鲸渲的竞争对手不是 Three.js 本身，而是「AI 用 Three.js 写游戏时那个看不见画面、复现不了问题的过程」。

## 2.5 开发初期的目标平台（已定）

**开发初期只针对 macOS 上的 Apple M4 及更新的芯片做设计和调优**，包括 M4、M4 Pro、M4 Max 和之后的 M 系列。
- 浏览器：
  - sikeoop 内置浏览器（Electron 44，WebGPU 底层走 Metal）；
  - Chrome / Edge（Dawn → Metal）；
  - Safari 26。
  - 三者都要能跑；性能基准以 sikeoop 内置浏览器为准。
- 其他平台（Windows 和各家独显、Intel Mac、M1–M3、手机）**这一阶段不保证**，也不为它们做专门优化。代码按 WebGPU 标准写，不使用任何只在 Apple 上才有的私有行为，以后扩展到别的平台时不用推倒重来。

**按 Apple 芯片的 GPU 特点来设计：**

| 特点 | 对鲸渲的影响 |
|---|---|
| **分块渲染（TBDR）**：屏幕切成小块，在片上缓存里完成着色 | 临时渲染目标尽量 `loadOp: clear` 加 `storeOp: discard`，不必要的结果不写回内存；尽量少切换渲染目标、少拆 pass；深度预渲染（depth prepass）默认不做 |
| **统一内存**：CPU 和 GPU 共用同一块内存，带宽是主要瓶颈 | 粒子属性尽量压缩存储，颜色和寿命用 16 位或打包格式；后期链降采样尽早做；拿带宽省下来的余量换粒子数量 |
| **SIMD 宽度 32** | 计算着色器的 workgroup 取 64（两组 SIMD），归约和前缀和按 32 线程一组设计 |
| **支持 `shader-f16`**（Chrome、Electron 的 Mac 版都有） | 粒子模拟里颜色、大小、寿命这些对精度不敏感的部分用 f16；位置和速度保持 f32 |
| **GPU 计时**：Chrome 系里有 `timestamp-query`，精度经过取整；Safari 能不能用以实测为准 | `inspect()` 里的耗时标明精度；没有计时能力时，退回用 CPU 侧的帧时间 |

## 3. 目标用户和场景

- **第一类用户：sikeoop 里的 AI 和人。** 用户说一句话，AI 用鲸渲写出带炫酷特效的网页游戏，再自己试玩、截图、修 bug。
- **第二类用户：手写代码的网页游戏和互动开发者。** 他们看重的是 GPU 粒子、shader 特效库、渲染图，以及清楚的报错。
- **典型作品**：
  - 弹幕射击、动作和休闲游戏；
  - 音乐可视化；
  - 活动页和产品页里的特效；
  - 2.5D 场景。
- **不追求的**：3A 级 3D 大作、开放世界、主机级画质。这些是 Unity、Unreal 的地盘。

## 4. 技术原则（以后有分歧，按这几条判断）

1. **只走 WebGPU。** 不做 WebGL 降级。不支持的浏览器给一个清楚的提示页，不硬撑。
2. **GPU 能做的，不交给 CPU。** 粒子、排序、剔除、mipmap 都用计算着色器；热路径上 CPU 不读回 GPU 数据。
3. **一切渲染都是渲染图里的 pass。** 有名字、有读写声明、有计时。人能看懂，AI 能读懂，引擎也能自动优化。
4. **确定性优先。** 凡是会让同样输入渲染出不同结果的东西（时间、随机、异步加载顺序），都要能固定下来。
5. **报错要能直接读懂。** 每个错误都写清楚：在哪里、为什么、怎么修。
6. **核心依赖少，生态靠互通。** 鲸渲核心只依赖数学库 `wgpu-matrix`（MIT）。其他渲染库不打进核心，而是通过第 8.5 节的「互通包」按需接入，用户用哪个就装哪个。
7. **API 小而直白。** 宁可少几个功能，也要让 AI 读一遍说明就能写对。每个公开 API 都要有可以运行的示例。

## 5. 不做什么（至少到 P3 之前）

- 不做 WebGL 兼容层。
- 不做物理引擎、声音、网络、可视化编辑器。这些交给现成库，或者以后作为独立模块做；鲸渲只负责渲染。
- 不兼容 Three.js 的 API。
- 不追求 3D 写实画质（PBR 全家桶、全局光照、光线追踪）。
- 移动端 P0 不做承诺，先保证桌面浏览器。

## 6. 技术选型

| 方面 | 选择 |
|---|---|
| 语言 | TypeScript（严格模式），着色器用 WGSL |
| 图形 API | WebGPU；可选特性按需开启：`timestamp-query`、`shader-f16`、`float32-filterable` |
| 构建 | Vite（开发服务器、打包和 shader 热重载）；产物是 ESM 格式的包 |
| 测试 | CPU 逻辑用 vitest；GPU 部分用确定性截图比对和 `inspect()` 性能断言，在 sikeoop 内置浏览器里跑 |
| 依赖 | `wgpu-matrix` |
| 协议 | 打算用 MIT 开源（待定，见第 10 节） |

## 7. 开发方向

### 7.1 主线：先做出能玩的效果，再扩展

```
P0 底座 ─→ P1 百万粒子 ─→ P2 特效与后期 ─→ P4 接进 sikeoop
                                         ↘ P3 3D（看需求）
```

- **P0 底座**：设备、资源、shader 系统、渲染图、实例化精灵、`inspect()`、确定性模式。
- **P1 GPU 粒子**：鲸渲的招牌。发射、模拟、整理、间接绘制全部在 GPU 上，配各种力场和碰撞。
- **P2 特效与后期**：shader 特效库（溶解、描边、扭曲、水波、扫光等）、HDR、Bloom、色调映射、LUT、2D 灯光。
- **P4 接进 sikeoop**：P2 做完就接，不等 3D：
  - 「WebGPU 游戏」项目模板；
  - 给 AI 的使用说明（作为一个技能）；
  - 截图回归接进「测试与回归」；
  - 性能面板。
- **P3 3D**：glTF、简化版 PBR、阴影、GPU 剔除。等真有 3D 游戏的需求再开工。

### 7.2 每个阶段的交付标准
- 每个功能至少有一个可以运行的示例，示例本身也是验收场景。
- 每个示例都有一张确定性截图作为基准，以后改动导致图变了，测试就会报出来。
- 每个阶段都有性能数字，同一份基准跑在固定的机器上。

### 7.3 性能目标（基准机器：MacBook，M4 基础款 10 核 GPU；sikeoop 内置浏览器；1080p 画布）

M4 Pro / Max 只做加分项，不作为验收依据：基础款能达标，往上的机型自然没问题。

| 指标 | 目标 |
|---|---|
| 实例化精灵 | 10 万个，60 帧 |
| GPU 粒子 | 100 万个，60 帧（模拟 + 绘制不超过 6ms）；120Hz 屏上 50 万个跑满 120 帧 |
| 后期整条链 | 不超过 2ms |
| 首帧时间 | 不超过 300ms（不算资源下载） |
| CPU 每帧开销 | 不超过 2ms |
| 引擎包体积（gzip） | 核心不超过 60KB，粒子不超过 20KB，后期不超过 20KB |

## 8. 和 sikeoop 怎么配合

- **AI 写游戏**：sikeoop 内置一份「鲸渲使用说明」技能，AI 写代码时照着用，不瞎编 API。
- **AI 看游戏**：内置浏览器的工具读 `inspect()` 和截图，AI 就知道掉帧发生在哪个 pass、shader 哪一行写错了。
- **AI 测游戏**：确定性模式加操作回放，变成「测试与回归」里的检查项。
- **AI 做素材**：以后接上图片和音效生成，以及 PhotoCraft 修图，鲸渲负责渲染这些素材。

## 8.5 生态互通：现有渲染库作为配套

现有的渲染库全部纳入鲸渲生态，但**不打包进核心，也不让核心依赖它们**。原因有四个：
- 全部打进来，包体会从几十 KB 涨到几 MB；
- 两套渲染器同时抢一块画布、一个 GPU 设备，会互相打架；
- 各家版本更新节奏不同，任何一家升级都可能把鲸渲弄坏；
- 有些协议根本不允许，比如 Unity、Construct 是商业软件。

纳入的方式分三种，按库的情况选：

**A. 互通包（运行时配合用，单独安装）**

每个互通包是一个独立的 npm 包，只在用户装了对应的库时才有用。原理是两边共用同一个 `GPUDevice`：鲸渲的粒子和后期直接画进对方的画面，或者把对方的画面当成鲸渲渲染图里的一个输入。

| 互通包 | 对接的库 | 能做什么 | 优先级 |
|---|---|---|---|
| `@sikeoop/jingxuan-three` | Three.js（WebGPURenderer） | 在 Three.js 场景里放鲸渲的百万粒子；用鲸渲的后期链处理 Three.js 的画面；共用深度，让粒子能和 3D 物体碰撞 | 高（用户最多） |
| `@sikeoop/jingxuan-pixi` | PixiJS v8（WebGPU） | 鲸渲粒子和 shader 特效当成 Pixi 的显示对象用 | 高（2D 主力） |
| `@sikeoop/jingxuan-babylon` | Babylon.js（WebGPU） | 同 Three.js 的做法 | 中 |
| `@sikeoop/jingxuan-playcanvas` | PlayCanvas（WebGPU） | 同上 | 中 |
| `@sikeoop/jingxuan-phaser` | Phaser | Phaser 现在走 WebGL，共用不了 GPU 设备：鲸渲画到一张离屏画布，再当贴图贴回 Phaser，有一帧延迟 | 低 |
| `@sikeoop/jingxuan-r3f` | React Three Fiber | 在 `jingxuan-three` 外面包一层 React 组件 | 低 |

- 第一批只做 Three.js 和 PixiJS 两个，其他的等有人用再做。
- 每个互通包都有一个可以运行的示例，并固定支持对方的某几个大版本。

**B. 配套库（鲸渲不做的部分，在文档和模板里推荐搭配）**

| 方面 | 推荐 |
|---|---|
| 物理 | Rapier（3D 和 2D）、Jolt、matter.js（2D） |
| 声音 | Howler.js；做音乐可视化用 Web Audio 或 Tone.js |
| ECS 架构 | bitECS、miniplex |
| 多人联机 | Colyseus |
| 动画 | GSAP、Spine 运行时、Lottie |

- 「WebGPU 游戏」项目模板里预置物理和声音的接法。给 AI 的使用说明里写清楚：什么时候该用哪个。

**C. 参考实现（只借鉴算法，不当依赖用）**

开源协议允许、做得又好的实现，拿来当设计参考。代码不直接复制；确实要移植某段时，在源文件里注明出处，并把原协议附进 `THIRD_PARTY_NOTICES.md`。

| 参考对象 | 借鉴什么 |
|---|---|
| Three.js（MIT）的 WebGPURenderer 和 TSL | 节点式 shader 的组织方式，WebGPU 资源的生命周期管理 |
| Babylon.js（Apache-2.0） | GPU 粒子系统、Inspector 调试面板的信息组织方式 |
| PlayCanvas（MIT） | 渲染图、体积控制 |
| PixiJS v8（MIT） | 2D 批量绘制，WebGPU 下的 BindGroup 复用 |
| Orillusion（MIT） | 原生 WebGPU 引擎的整体架构，计算着色器的用法 |
| Bevy（MIT/Apache）和 wgpu | 渲染图和 ECS 的设计 |

**不纳入的：**
- 商业闭源的：Unity、GameMaker、Construct、Wonderland Engine。协议不允许，也没有源码可以参考。
- 已经停止维护的：Egret、Hilo。
- 只有编辑器、主要靠导出用的：Cocos Creator、LayaAir、Godot、Defold。它们是另一条产品路线，以后 sikeoop 可以单独做「Godot 接入」，不经过鲸渲。

## 9. 风险和应对

| 风险 | 应对 |
|---|---|
| 只在 M4 以上调优，换到别的平台可能性能不达标、表现不一样 | 已经接受（见第 2.5 节）。代码只用 WebGPU 标准能力；启动时把实际上限记进 `inspect()`；超出上限就自动缩小粒子容量。扩展到其他平台时，作为单独一个阶段来做 |
| Safari 和 Chrome 在 Mac 上的 WebGPU 实现不同（WebKit vs Dawn） | 每个示例的截图基准在三个浏览器里各存一份；性能只以 sikeoop 内置浏览器为准 |
| 一个人做，工作量大 | 严格守住第 5 节「不做什么」；P3 按需求再开工；互通包第一批只做 Three.js 和 PixiJS |
| 对接的库升级后，互通包被弄坏 | 每个互通包写明支持对方哪些版本，CI 固定用这些版本跑示例；对方出大版本时单独适配 |
| 确定性在不同芯片、不同浏览器上做不到逐像素一致 | 同一台机器、同一个浏览器内做严格比较；换机器或换浏览器用容差比较 |
