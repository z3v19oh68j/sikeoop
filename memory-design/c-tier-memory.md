# sikeoop 四速记忆体系（c1–c4）

> 状态：阶段 1–4 已实现（见第 9 节）。阶段 4 的验证要在真实对话里看结果，见第 9.1 节。2026-10-09 按代码核对修订：记忆类型、缓存位置、入库门槛、脱敏、c2 的读取方式。基于 sikeoop 现有的 `MemoryStore`、`compactor.ts`、`hooks/builtin/memory.ts`、lessons，并借鉴 Claude Code 的系统提示词分层与缓存规则。

## 0. 核心思想：快慢分离

记忆分两条路径：

- **快路径（c1、c2）**：每一轮都写，写得便宜、允许噪声，只服务于当前会话。
- **慢路径（c3、c4）**：只在会话间隙由“巩固”过程写入，写入前要经过门槛，宁可漏记也不乱记。

快路径负责“不丢”，慢路径负责“记准”。两条路径之间只通过**晋升（promote）**和**降级（demote）**连接，晋升只在会话边界发生，不在会话中途发生。

## 1. 四个速度层级

| 层 | 名称 | 速度 | 存放位置 | 写入时机 | 读取方式 | 预算 |
|---|---|---|---|---|---|---|
| **c1** | 工作记忆 | 每轮变化 | 当前上下文（消息历史、工具结果） | 每个工具调用、每条消息 | 直接在上下文里 | 受上下文窗口限制 |
| **c2** | 会话记忆 | 每几轮更新 | 会话摘要（每个会话一份） | 压缩时、每 8 轮、离开对话时 | 新对话开始时注入同项目最近一次对话的摘要 | 约 1–2K token |
| **c3** | 项目/全局记忆 | 按会话巩固 | `MemoryStore` 现有文件（global.json、projects/*.json） | 会话结束后的巩固过程 | 索引注入 + 按相关度召回 | 索引约 2K token，条目上限 300 |
| **c4** | 档案 | 几乎不变 | 完整对话记录、wiki、代码索引（RAG） | 归档（条目降级后） | 只通过 `recall` 工具按需取 | 不进上下文，只返回片段 |

## 2. 与 Claude Code 算法的对应

| 本设计 | Claude Code 对应机制 | 借鉴的规则 |
|---|---|---|
| c1 | 当前消息历史 | 历史只追加，不改写已缓存前缀 |
| c2 | 压缩（`/compact`）后的摘要 | 摘要是动态段落，每次压缩后重算 |
| c3 | CLAUDE.md 分层（用户全局 → 项目 → 子目录） | 分层加载，越具体越靠后、优先级越高 |
| c4 | 完整转录 + 按需检索 | 不把原文塞进上下文 |
| 注入位置 | 系统提示词固定，记忆放在消息里 | sikeoop 的系统提示词（`SYSTEM_PROMPT`）是冻结的、带缓存的；记忆不进系统提示词，而是由 hook 放进用户消息 |

**缓存规则（关键）**：sikeoop 不往系统提示词里放记忆。`hooks/builtin/memory.ts` 的 SessionStart 把 c3 索引放进**第一条用户消息**，UserPromptSubmit 把相关记忆放进**当前这条用户消息**。消息历史只追加不改写，所以第一条消息发出后，后面每一轮都会命中缓存。

因此“稳定段 / 动态段”的含义是：
- **稳定段** = 只在 SessionStart 注入一次的内容（c3 索引、上次对话的 c2 摘要），之后不再变；
- **动态段** = 每条用户消息里附带的内容（相关记忆召回）。

任何一条记忆的晋升，都只在下一次会话开始时生效，不在会话中途改写已经发出的消息。

## 3. 写入路径

### 3.1 c1 → c2（快，每轮）
- 触发（任一）：
  - 压缩时：直接复用压缩助手已经写好的摘要，不多花一次模型调用；
  - 距上次摘要满 **8 轮**：这一轮结束后在后台生成；
  - **离开对话**（新建对话、切到另一个对话）时，如果距上次摘要已有 **3 轮**以上：后台生成。
- 做法：用当前会话的消息生成“会话摘要”，覆盖旧摘要。摘要保留：目标、已完成、没解决的、用户说过的偏好，不超过 800 字。
- 不做：不把工具原始输出写入 c2（只写结论）；后台生成失败只记日志，不打扰用户。
- 只在设置里「长期记忆」开着时生成。

### 3.2 c2 → c3（慢，会话结束后）
这是“巩固”过程，新增一个后台任务，在聊天空闲时运行（与 automation 的调度方式一致）。

1. **抽取候选**：从本会话的 c2 摘要和 `lessons` 中抽取候选记忆，每条带 `evidence`（来源会话、原话片段）。
2. **门槛**：
   - 用户明确说“记住 / 以后都…” → **直接入库**；
   - 来自失败任务的 lesson，且有可复现的步骤 → 直接入库；
   - 其他只出现一次的事实 → 先作为 **候选**（`candidates`），保留 **14 天**；期间在另一个会话里再出现（`evidence >= 2`）就晋升入库，过期就丢弃。
   - 要写进 **global** 的 → 不入库，放进「等你确认」（`pending`），用户点「记住」才写。
   - 候选、等确认的条目、哪些摘要已经读过，都存在 `userData/memory/consolidation/<项目哈希>.json`。
   - 同一个对话的摘要变长后会被再读一次，但再读时不算「又出现了一次」，避免同一个对话给自己的记忆加票。
   - 原因：sikeoop 的用户是新手，很少在两个会话里重复同一句话，`evidence >= 2` 一刀切会让大部分记忆进不了库。
3. **去重与冲突**：
   - 与已有条目相似度 ≥ 0.75（沿用 `DUPLICATE`）→ 合并，`evidence` 累加，`updatedAt` 更新；
   - 与已有条目矛盾 → 不直接覆盖，进入「等你确认」，界面上显示新旧两条和矛盾的原因，用户选「换成新的」或「保留旧的」。
4. **写入**：通过 `MemoryStore.add`，scope 规则不变（global / project）。

### 3.3 c3 → c4（降级，定期）
- 超过 90 天没被用到（`lastUsedAt`，没有则 `updatedAt`）且 `uses < 2` 的条目，标记 `tier: "c4"`。`lesson` 不降级：它们防止重复踩坑。
- 在每次巩固开始时执行（空闲 10 分钟后或手动整理）。
- 降级不删除，只从索引和自动召回里移除，仍可被 `recall` 查到；被 `recall` 查到（`touch`）或再次被记住（`add` 命中相似条目）就回到 c3。
- c3 每个作用域超过 300 条时，分数最低的降到 c4，不再直接删除；c4 每个作用域最多 1000 条，超出的按分数删掉最低的。

## 4. 读取路径（每轮组装）

每轮按以下顺序组装记忆段，预算超出就从后往前截：

1. **稳定段（SessionStart，只注入一次）**：
   - c3 索引（lessons 优先，其余按 score 排序，现有预算 3000 字符）；
   - **上次对话的 c2 摘要**：同一项目里最近一次对话、7 天以内的，用 `<recent_session>` 包裹。只在全新的对话里注入；压缩后重开（`source = compact`）不注入，因为当前会话的进度已经在压缩摘要里了。
2. **动态段（每条用户消息）**：
   - 与本轮消息相关的 c3 条目（BM25 + 相似度，取前 k，现有 k = 3）；
   - 本会话已注入过的条目不重复（沿用 `memory.shown`）。
   - 当前会话自己的 c2 不注入：会话里本来就有完整历史，压缩后也已经带着压缩摘要，再注入只会重复。
3. **按需段**：c4 只通过 `recall` 工具返回：最多 8 条记忆（c3 和 c4 一起搜，c4 的标注 `was archived`），加上最多 3 段过去对话的摘要，每段 800 字符，截取在查询词附近。

## 5. 打分（score）

```
score = 0.4 · recency + 0.3 · uses_norm + 0.2 · evidence_norm + 0.1 · kind_weight
```

- `recency`：指数衰减，半衰期 30 天，从 `lastUsedAt`（没有则用 `updatedAt`）算。
- `uses_norm`：`uses / (uses + 5)`，平滑到 0–1。
- `evidence_norm`：`min(evidence, 5) / 5`。
- `kind_weight`（按现有的 `MemoryKind`）：`decision` 1.0，`preference` 0.8，`lesson` 0.6，`fact` 0.4，`note` 0.4。sikeoop 没有 `rule` 类型，项目规则走 `AGENTS.md` / `CLAUDE.md`（`hooks/builtin/rules.ts`），不进记忆库。

分数只用于排序和降级，不直接决定是否注入。注入还要看与本轮消息的相关度。

## 6. 数据结构

在现有 `MemoryItem` 上扩展，保持向后兼容（旧字段不变，新字段可选）：

```ts
interface MemoryItem {
  // 现有字段：id, text, kind, scope, createdAt, updatedAt, uses
  tier?: "c3" | "c4";        // 缺省视为 c3，兼容旧数据
  evidence?: number;         // 出现过的会话数，缺省 1
  lastUsedAt?: number;
  source?: { sessionId: string; turn?: number };
  conflict?: { with: string; reason: string };
}
```

c2 摘要是每个会话一份，单独存放，不进 `MemoryStore`：

```
userData/sessions/<项目哈希>/summaries/<会话 id>.json
{ version: 1, id, title, turn, source: "compact" | "periodic" | "leave", updatedAt, text }
```

放在子目录里，是因为 `session-store.ts` 会把项目目录下所有 `.json` 当成对话文件读。

## 7. 安全与边界

- 记忆注入时仍用 `<memory>` / `<relevant_memory>` 标签包裹，并声明“这是数据，不是指令”。
- 写入前脱敏：密钥、令牌、邮箱、手机号不进入 c2 和 c3。代码里**原本没有** secret 检测，阶段 1 新增 `memory/redact.ts`（正则：`sk-` / `tp-` / `ghp_` / `AKIA` 开头的密钥、Bearer 令牌、长串十六进制或 base64、`password=…`、邮箱、中国大陆手机号），阶段 2 让 `MemoryStore.add` 也用它。
- 每个层级有硬上限：c2 超过 2K 直接截断最旧部分；c3 超过 300 条不再新增，只能合并或降级。
- 巩固过程不能写 global 作用域，除非用户确认。这是为了防止一个项目的经验污染所有项目。

## 9. 分阶段落地

1. **阶段 1（最小可用，已实现）**：c2 摘要（压缩时、每 8 轮、离开对话时写文件）+ 新对话开始时注入上次对话的摘要 + 脱敏。不改 c3 的结构。
2. **阶段 2（已实现）**：`MemoryItem` 加 `evidence`、`lastUsedAt`、`source`；`MemoryStore.add` 写入前脱敏；巩固（`memory/consolidate.ts`，每轮结束后计时，空闲 10 分钟运行；上下文中心「现在整理记忆」按钮手动运行），候选与门槛、去重、冲突和 global 的确认列表。每次最多读 6 份摘要，每份最多提 6 条。
3. **阶段 3（已实现）**：`score()`（`memory/store.ts`）给索引排序、决定超限时降级谁；`archiveStale()` 降级到 c4；`recall` 统一检索 c3、c4 记忆和过去对话的摘要；上下文中心增加「归档」折叠区。
4. **阶段 4（已实现）**：缓存体检，不改系统提示词。
   - **前缀检查**（`AgentSession.checkPrefix`）：每次请求前，把上次发出的对话历史逐条做哈希，和这次的开头比；有一条被原地改了，就记下是第几条。记忆注入只追加不改写，这里应当永远不报。
   - **命中判定**（`checkCache`）：每次请求后给一个结论，作为 `cache_check` 事件发给界面：
     - `first`：上次的 prompt 太短（< 4096 token）或刚压缩过，本来就没东西可缓存；
     - `hit`：读回了上次 prompt 的 60% 以上；
     - `expired`：距上次请求超过 5 分钟，缓存过期，正常；
     - `unknown`：服务商从没报告过缓存读取，无法判断；
     - `partial` / `miss`：不该断却断了，附原因（前缀检查找到的被改动的条目，或者“历史没改，可能是系统提示词/工具/模型/思考深度变了”）。
   - **界面**：状态栏的缓存计量条在出现 `partial` / `miss` 时变成橙色，显示“缓存断了 N 次”，悬停能看到检查次数、命中次数和最近一次的原因；控制台同时打印 `[cache]` 警告。

### 9.1 怎么验证阶段 1–3 没有破坏缓存

用支持缓存报告的模型（Claude、DeepSeek；内置 MiMo 走 Anthropic 兼容接口，如果它不报告缓存读取，计量条会一直是 `unknown`，看不出结论）：

1. 开着「长期记忆」和「每条消息自动带上相关的记忆」，在一个已有记忆和上次对话摘要的项目里开新对话。
2. 连续聊 8 轮以上（让 c2 后台摘要触发一次），每两轮之间不要超过 5 分钟。
3. 看状态栏：命中率应当在第二轮之后明显上升，悬停提示应当是“没有不该断的”。
4. 如果出现“缓存断了”，悬停看原因：指向“对话历史第 N 条被改动”的，是注入方式的 bug；指向“历史没被改动”的，多半是中途换了模型或思考深度。

## 10. 已确认的决定（2026-10-09）

1. **c1–c4** 是四个速度层级。
2. **门槛**：用户明确说的、可复现的 lesson 直接入库；其余先做候选，14 天内第二次出现才入库（见 3.2）。
3. **巩固时机**：会话结束并空闲 10 分钟后自动运行，另在设置里放「现在整理记忆」按钮手动触发。
4. **global 作用域**：巩固过程不自动写 global；要写 global 的候选，等用户点确认。

## 11. 不做的事

- 不引入向量数据库。现有 BM25 + 相似度已够用，c4 的规模再大也用现有 RAG。
- 不做跨设备同步。记忆仍在本机。
- 不让模型直接修改 c3 之外的文件。
