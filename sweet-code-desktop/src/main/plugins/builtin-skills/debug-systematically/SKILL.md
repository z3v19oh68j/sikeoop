# 系统化调试

乱试是最慢的修法：每试一次，用户都要确认一次改动、跑一次命令，还可能引入新问题。**先找到原因，再动手修。**

## 第 1 步：读懂报错

- 把报错从头读到尾。最有用的通常是：错误类型、错误信息、**第一个指向用户自己代码的文件和行号**（跳过 node_modules 里的那些行）。
- 用 `read_file` 打开那个位置，看前后的代码。
- 用户只说「不行了」「坏了」时，问一句：具体看到了什么？有没有报错？是在终端里还是浏览器里？也可以让用户点终端的「帮我看看」把输出发过来。

## 第 2 步：稳定复现

- 找到一个**每次都能触发问题**的操作或命令。复现不了就先别修，否则修没修好都不知道。
- 能用一条命令复现最好（比如跑某个测试、运行某个脚本），之后验证修复也用它。

## 第 3 步：缩小范围，找根本原因

- 问「最近改了什么？」：用户说「之前还好好的」时，查看最近改动（有 git 就用 `git diff` / `git log -5 --stat`）。
- 顺着数据往回找：错误的值是从哪来的？上一步是对的吗？再上一步呢？
- 用 `search` 找相关的函数、变量在哪里定义、在哪里被调用。
- **一次只验证一个猜测**：写下「我认为原因是 X，因为 Y」，然后用最小的办法证实它（读代码、加一行 `console.log`、跑一个小命令）。
- 修的是原因，不是症状。比如数据是 `undefined` 时，不要只加一个 `if` 把报错盖住，要找到它为什么是 `undefined`。

## 第 4 步：修，然后验证

- 做最小的改动来修根本原因。
- 用第 2 步的复现方法再跑一遍，确认问题没了。
- 加过的调试用 `console.log` 记得删掉。
- 能写测试的，用 `test-first` 补一个测试，防止它再回来。

## 卡住了怎么办

- **同一个问题修了 2 次还没好**：停下来，不要再试第 3 种改法。重新从第 1 步开始，把你已经排除的可能列给用户看，说清楚现在知道什么、不知道什么。
- 原因在第三方库或环境（版本不兼容、没装依赖、网络）：直接告诉用户，给出具体的命令或步骤。

## 给用户的说明

修好后用三句话说清楚：
1. 问题是什么（大白话）
2. 原因是什么
3. 改了哪里、以后怎么避免
