# 高效开发总流程

这是一套组合技能的入口。目标：**少返工、少猜、每一步都能验证**。新手最怕的是 AI 一口气改了一大堆，结果跑不起来又不知道哪里坏了。

## 先判断任务大小

| 任务 | 例子 | 怎么做 |
|---|---|---|
| 小 | 改个文案、调个颜色、修一个明确的报错 | 直接做，做完走 `verify-before-done` |
| 中 | 加一个按钮和它的功能、改一个页面 | `plan-first`（简短版）→ 做 → `verify-before-done` |
| 大 | 新做一个模块、要改 3 个以上文件、需求说不清 | `plan-first` → `task-board` → 按任务逐个做 → 每个任务都 `verify-before-done` |
| 出 bug | 报错、结果不对、「之前好好的」 | `debug-systematically` |

拿不准就按大一级的处理。

## 完整顺序（大任务）

1. **plan-first**：问清楚要什么，写出计划，等用户点头。
2. **task-board**：把计划拆成小任务写进 `TASKS.md`，每个任务做完都能单独验证。
3. 一次只做一个任务：
   - 有测试框架、逻辑容易出错的地方 → **test-first**
   - 遇到报错 → **debug-systematically**，不要乱试
4. 每个任务做完 → **verify-before-done**：真的跑一遍，看到结果再说「好了」。
5. 一组改动完成 → **self-review** 自查一遍 diff。
6. 项目用 git 的话 → **git-checkpoint** 存个档，方便以后回退。
7. 更新 `TASKS.md`，告诉用户做到哪了、下一步是什么。

## 几条总规矩

- **一次一件事**：不要同时改好几个不相关的东西。改动越小，用户越容易看懂和确认。
- **先读后改**：动手前用 `read_file` / `search` 看真实代码，不要凭印象。
- **命令要省**：每条命令用户都要点确认，所以想清楚再跑，能一条解决的不要拆成三条。开发服务器这种一直运行的命令写进 bash 代码块，让用户点「在终端运行」。
- **说人话**：每完成一步，用一两句大白话告诉用户做了什么、怎么看效果。
