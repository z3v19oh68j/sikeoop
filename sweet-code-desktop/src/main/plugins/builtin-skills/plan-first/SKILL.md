# 先规划再动手

改错方向的代价远大于多问一句。这个技能保证你在写第一行代码之前，你和用户想的是同一件事。

## 第 1 步：看懂现状（自己做，不打扰用户）

- 用 `list_files`、`search`、`read_file` 找到和需求相关的文件，看清楚现在是怎么写的。
- 记下：入口文件在哪、要改的大概是哪几个文件、项目用了什么框架和写法。
- 能从代码里查到的事，不要问用户。

## 第 2 步：只问真正要用户决定的事

- **一次最多问 3 个问题**，每个问题给出选项和你的推荐，比如：
  > 1. 点击后是跳到新页面，还是弹一个小窗？（推荐弹窗，改动小）
- 需求已经很清楚就跳过这一步。

## 第 3 步：写计划

用这个格式直接回复给用户（中任务）；大任务另外存到 `docs/plans/<日期>-<主题>.md`：

```markdown
## 要做什么
一两句话说清楚目标和做完后的样子。

## 怎么做
1. 改 `src/xxx.ts`：……
2. 新建 `src/yyy.tsx`：……
3. ……

## 怎么验证
- 运行 ……，应该看到 ……
- 打开页面点 ……，应该 ……

## 不做的事
- ……（明确范围，防止越改越多）
```

要点：
- 每一步写清楚**改哪个文件、改什么**，不要写「优化代码」这种空话。
- 「怎么验证」必须是能真正执行的操作。
- 方案有明显取舍时，给 2 个方案对比一下，说出你推荐哪个、为什么。

## 第 4 步：等用户点头

- 计划发出后**停下来**，问「这样可以吗？」。用户同意或提出修改后再动手。
- 用户说「直接做」「你决定」时，可以不等，但还是先把计划简短说一遍。
- 大任务接着用 `task-board` 把计划拆成任务。
