# 先写测试再写代码

测试是「自动帮你检查」的小程序。先写测试，等于先把「做对了是什么样」写下来，之后每次改代码都能一秒钟知道有没有改坏。

## 什么时候用

- 适合：计算、格式转换、数据筛选排序、表单校验、工具函数，还有能稳定复现的 bug。
- 不适合（跳过，改用 `verify-before-done` 手动验证）：纯样式、布局、文案、一次性脚本。
- 项目还没有测试框架时，先问用户要不要加。不要自作主张装一堆依赖。推荐：
  - Vite / 前端项目 → Vitest
  - 普通 Node 项目 → Node 自带的 `node --test`，不用装任何东西
  - Python → pytest

## 循环：红 → 绿 → 整理

1. **红**：写一个测试，描述你想要的行为。运行它，**亲眼看到它失败**，并且失败原因正是「功能还没写」。
   - 如果测试直接通过了，说明它什么都没测到，要重写。
2. **绿**：写**刚好够**让测试通过的代码，不多写。再运行，看到通过。
3. **整理**：代码有重复、命名不清楚就整理一下，再跑一次，确认还是通过。

每个循环只加一个行为。下一个行为再开一个循环。

## 写测试的要点

- 一个测试只检查一件事，名字用大白话写清楚，比如 `空密码时返回"请输入密码"`。
- 别忘了边界情况：空值、0、负数、特别长的输入、中文。
- 修 bug 时：先写一个能复现这个 bug 的测试（红），再修（绿）。这样同一个 bug 以后不会再回来。

## 跑测试

- 用 `run_command` 只跑相关的测试文件，比如 `npx vitest run src/utils/price.test.ts`。全部测试留到最后一起跑。
- 不要用 watch 模式（`vitest` 不带 `run`），那会一直运行不结束。
- 告诉用户结果时，贴出关键的那一行（几个通过、几个失败），不要贴整屏输出。
